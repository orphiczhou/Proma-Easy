# Spike 实验协议 · 架构阶段架构探索实验规范

> 版本：v1.0 | 日期：2026-09-18 | 随六品类模版 v2.0 迁移定稿（平台 v0.17.126）
> 上游依据：平台知识库《工程模版改进-v1》00-现状差距分析缺口 G4、01-模版结构规范-v2 §3.5/§6（2026-09-18）
> 定位：定义"架构师在模版知识不足时，派子会话做架构探索实验（Spike）"的完整流程。本文是协议正文；各品类模版 §6 只引用本文，不重复。

---

## 1. Spike 是什么、解决什么

**Spike = 一次有时间盒、有验收判据、产物必须工程化落盘的小型探索实验。**

解决的问题 [实证，2026-09-17 夜间实测]：
- 架构师对"本机环境能不能跑通某方案"没有把握时，只能凭训练记忆拍板，错误在 8 轮验收中才暴露；
- 现场试错的过程知识（试了什么、为什么失败）随会话消散，开发和测试无法复用；
- 实验环境和脚本没有规范位置，下一轮验证要重建环境。

Spike 的三个产出承诺：**结论**（方案排序+判据）、**环境**（可一键重建的脚本）、**证据**（落盘的运行结果）。

## 2. 触发判据（何时必须 Spike）

架构师在架构设计阶段对某个技术决策同时满足以下三条时，**必须**派 Spike，不得直接拍板：

| # | 判据 | 反例（不需要 Spike） |
|---|------|---------------------|
| T1 知识缺口 | 该决策点不在品类模版的 §2 组件清单 / §7 坑库 / §8 标杆映射覆盖范围内，或仅有 [推断] 级知识 | 模版已有 [实证] 条目直接引用 |
| T2 决策影响 | 该决策会影响架构选型、组件选型或验收方案（不是实现细节） | 纯代码风格问题走常规开发 |
| T3 可时间盒 | 能在时间盒（见 §6）内设计出一个可判定的实验 | 需要数周调研的开放问题 → 拆分或降级为"带风险的假设"记录 |

典型触发场景（本轮实测映射 [实证]）：
- "X11 下 CJK 注入到底哪条路可行？" → SPIKE 候选（XkbSetMap / AT-SPI 两条 [推断] 路线，见 desktop-app.md 坑库）
- "远程桌面无麦克风环境怎么自证音频采集链路通？" → 已由实测解决（xrdp-sink.monitor 回环），应回填模版而非重做 Spike
- "该云端 ASR 端点到底支持哪些模型名？" → 已由实测解决（qwen3-asr-flash），同理回填

**触发权与并发行**：架构师拥有 Spike 派发权；同一架构阶段可并行派发多个 Spike（多个子会话互不依赖）；每个 Spike 独立编号。

## 3. Spike 任务书模板（架构师 → 子会话）

```markdown
# SPIKE-<NNN>-<slug> 任务书

## 1. 问题与假设
- 背景：一句话说明架构决策点（引用 PRD/架构文档路径）
- 问题：<待验证的具体问题，必须可判定>
- 假设 H1：<当前倾向的方案/预期结果>（可多个假设）

## 2. 环境约束
- 工作目录：<工程目录>/00_SPIKES/spike-<NNN>-<slug>/（所有产物必须落在此处）
- 机器环境：<已知 OS / 窗口系统 / 已装组件，引用品类模版 §2 探测结果>
- 允许安装：系统包须列出预期包名；禁止修改工程目录外既有文件
- 网络与凭证：<是否允许外网/云端 API；API key 的注入方式（环境变量），任务书中不得出现明文 key>

## 3. 实验要求
- 每个假设至少一个可重复执行的驱动脚本（setup + probe 分离，幂等）
- 探测/驱动结果必须落盘到 evidence/（JSON 或日志文件），不得只打印
- 遵守品类模版 §5.3 驱动断言规范（expected/actual 严格同串；崩溃隔离）

## 4. 产物清单（验收物）
- README.md：实验报告（结论/证据索引/方案排序与推荐）
- setup.sh|setup.ps1：环境安装脚本（幂等，可重复执行）
- probe.*：驱动脚本（输出 JSON 证据）
- evidence/：真实运行证据（文件，含时间戳）
- NOTES.md：试错轨迹（试过什么、为什么放弃——防止后人重复踩坑）
- env-manifest.md：环境清单（系统版本/包版本/pip npm 清单/关键环境变量名）

## 5. 验收判据（§6 细化）
- 结论明确（假设被证实/证伪，多方案给出排序与判据）
- 第三方可复现：照 README 执行 setup+probe 能得到同结论
- 证据完备：evidence/ 非空且与结论互相引用

## 6. 时间盒
- 执行 ≤ <N> 分钟 / ≤ <N> 轮子会话往返；超时立即止损，落盘部分结论并标记 PARTIAL

## 7. 禁止事项
- 不得修改 00_SPIKES/ 之外的任何现有文件
- 不得将未验证的结论写成确定性论断（用 [实证]/[推断] 标注）
- 不得在产物中记录明文密钥/隐私数据
```

## 4. 产物规范（工程目录标准落位）

```
<project-root>/
├── 00_SPIKES/                          ← Spike 总目录（v2 新增的标准工程目录）
│   ├── INDEX.md                        ← 全部 Spike 索引：编号/问题/结论一句话/状态[FULL|PARTIAL]
│   └── spike-001-x11-cjk-injection/    ← 每个 Spike 一个目录
│       ├── README.md                   # 实验报告（唯一入口）
│       ├── NOTES.md                    # 试错轨迹
│       ├── env-manifest.md             # 环境清单
│       ├── setup.sh                    # 幂等安装脚本
│       ├── probe.py / probe.sh         # 驱动脚本（输出 JSON）
│       └── evidence/                   # 证据文件（*.json / *.log / 截图 / 录像）
├── 06_TESTS/                           ← 既有测试目录：验收用例引用 Spike 证据（见 03 文档）
└── engineering.json                    ← 既有工程档案：登记 spike 元数据（见 03 文档）
```

规则：
1. `INDEX.md` 由架构师在验收每个 Spike 后更新，是后续所有会话发现既有实验的唯一入口。
2. Spike 产物是**工程交付物的一部分**（长期迭代型项目入版本库；快消型项目至少保留 INDEX.md 与各 README.md）。
3. 驱动脚本必须与 setup 分离且幂等——"实验资料和环境留给后面的开发和测试" [父会话根因判断原文] 的落地形态。

## 5. 执行流程（子会话视角）

```text
接收任务书
  → 读取品类模版 §2（组件环境清单）执行环境探测，落盘探测证据
  → 按 3.实验要求 写 setup + probe，先跑 setup（幂等）
  → 跑 probe，证据落盘 evidence/
  → 若假设被证伪：按 NOTES.md 记录轨迹，尝试下一假设（受时间盒约束）
  → 撰写 README.md 实验报告：结论 / 方案排序 / 判据 / 证据索引
  → 上行事件 done（附产物清单）或 blocked（附已尝试路径与卡点）
```

## 6. 验收判据与时间盒

### 6.1 验收判据（架构师逐条勾验）

| # | 判据 | 不通过的处理 |
|---|------|-------------|
| A1 结论明确 | 假设被证实/证伪；多方案有排序与判据 | 退回补一轮（计入时间盒轮次） |
| A2 可复现 | setup+probe 在干净上下文重跑得到同结论 | 修复脚本幂等性 |
| A3 证据完备 | evidence/ 非空、含时间戳、被 README 引用 | 补证 |
| A4 断言合规 | 符合品类模版 §5.3 三条硬规则 | 修驱动 |
| A5 边界合规 | 未越界修改文件；无明文密钥 | 违规即验收失败并记录 |

### 6.2 时间盒基准（建议值，可按品类调整）

| 项目模式 | 单 Spike 执行 | 返工上限 | 超时处理 |
|---------|--------------|---------|---------|
| 快消型 | ≤ 30 分钟 或 ≤ 6 轮工具往返 | 1 轮 | 立即止损，落盘 PARTIAL 结论 + 假设降级为风险记录 |
| 长期迭代型 | ≤ 2 小时 或 ≤ 12 轮 | 2 轮 | 同上；重要未决问题可申请架构师批准追加一个新 Spike |

止损原则：**PARTIAL 的 Spike 价值仍为正**——NOTES.md 的试错轨迹本身就阻止了开发/测试阶段重复踩坑 [推断，基于 G3/G4 根因]。

### 6.3 知识回填闭环（Spike → 模版）

架构师验收通过后必须执行两步：
1. **回填工程档案**：Spike 元数据与结论登记进 `engineering.json` 与 `06_TESTS` 引用（详细条文见 `03-架构阶段流程增强建议.md` §2/§3）。
2. **回填品类模版**：把结论按证据等级写入模版对应章节——
   - 组件环境新知识 → §2 组件卡片（新增或修订"已知坑"）
   - 验证方法新知识 → §5 闭环样例或 §5.4 降级验证
   - 坑 → §7 坑库新条目（状态从 [推断待验证] 升级为 [实证]，或直接新增实证条目）
   - 并在模版 CHANGELOG 记录来源 Spike 编号（如 `来源：SPIKE-001`）
