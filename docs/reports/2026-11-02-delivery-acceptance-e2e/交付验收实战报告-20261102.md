## 二、暴露的平台缺陷（建议落 Issue）

### P1-1 交付验收死锁（auto 审核 + 工程契约项目）
- 现象：`autoClarify.enabled=true` 时 `nanju-router-gate.ts checkNanjuAskUserRoute` 只放行 `确认·安装缺失组件`；而 `isAutoConfirmDeliveryProject` 显式排除有 `engineering.json` 的项目 → **工程类项目交付验收无任何路径**（交付门禁只认 ask-answer「满意交付」，路由又拒绝一切 AskUser）。
- 现场：番茄会话自主报告「平台级门禁死锁」，三条路径全被拦。
- 规避：临时关闭该项目 autoClarify（增加真人确认点，非绕过）。
- 修复候选：路由对 `getProjectDeliveryChallenge() !== null` 无条件放行（恢复 D7 §3② 交付挑战机器豁免，去掉 `enabled!==true` 谓词），或工程项目 auto on 走自动交付。

### P1-2 权限横幅按会话渲染导致「静默卡死」
- 现象：GWT 逐项批准横幅只在**该会话 chat 处于激活视图**时渲染；GUI 停在其它会话时横幅不可见、GWT 表现为「已在进行中」但无驱动进程、无报错、无进度（实测停滞 17 分钟以上）。
- 排查成本极高（误判为探测卡死/并发排队）。
- 建议：待决审批在侧边栏/全局给出角标或通知；或审批请求不依赖 chat 挂载。

### P1-3 见证新鲜度窗口（10 分钟）与交付链路时长竞态
- `ENGINEERING_REAL_MAX_EVIDENCE_AGE_MS = 10 * 60_000`；但「见证登记 → L1 续接（LLM 30–60s）→ GWT 重跑（1–2min）→ 交付询问 → 应答 → delivered」常逼近甚至超过窗口，实测番茄连续 3 轮「观察完成已超过新鲜度窗口」。
- 交付门禁在交付时**再次**校验见证新鲜度，故窗口必须在交付那一刻仍有效。
- 建议：延长窗口、或在交付时允许「同会话真人见证 + 当次 GWT pass」组合（不再要求 10 分钟内），或提供一键压缩流程。

### P1-4 L1 自动续接不可靠（`上一条消息仍在处理中`）
- GWT pass 后的交付验收续接（`setTimeout 1500` → `runRegisteredHeadlessAgent`）在多处失败：「上一条消息仍在处理中；这条消息未保存」，导致交付询问不出现；另有 `[南大护栏] 续接空闲巡检耗尽（会话长时间忙碌 600s）` 的挂起态。
- 建议：续接改排队重试（带退避），而非单次 1.5s。

### P1-5 未绑定协作子会话 Bash 被拒（W19）
- 现象：L1 委派的修复子会话（无 `sourceDelegationId` 标记）在工程工作区执行 `python3 drivers/...` 被 `checkUnboundSessionWriteGuard` 拒绝（实测 21 次），无法自跑验证。
- 建议：L2 委派子会话默认豁免 Bash（或白名单 `08_APP/drivers/**` 只读执行）。

### P1-6 AskUserQuestion 横幅交互为「选择 + 确认」两段式
- 选项按钮文本形如 `1满意交付可以交付使用…`，且需再点「确认」（或 Enter）。自动化/代点时精确匹配 `满意交付` 会失败且易漏确认。
- 建议：按钮暴露 `aria-label`/`data-option-value` 稳定标识；或支持单点即提交。

### P1-7 工程驱动契约的 storyId 校验（已按设计工作，但反馈可更早）
- 驱动 `checks[].storyId` 越界（US-05 未在 `covers`）会导致整项 `error`，且 stdout 仅保留 tail 摘要（完整输出未落盘），排障需回读驱动源码。
- 建议：`error` 时保留完整 driver stdout 到 evidence（而非 tail）。

### P1-8 `_project-info.json` 与注册表 `autoClarify` 双源
- `autoClarify` 实际在 `_nanju-projects.json`（`_project-info.json` 无该字段），排障易误判为「auto 未开」。

## 三、方法论复盘

- **必须让 L1 亲口声明确认标记**：直接向会话注入裸 `<!-- PHASE_ADVANCE: testing -->` 用户消息，consumer 会消费但 GWT 常停滞在批准阶段；由 L1 生成的 assistant 消息标记才是稳定路径（实测差异：停滞 17min vs 1min 完成）。
- 自动化栈最终形态（可复用）：
  1. **批准守护**（CDP）：周期性切换三个会话 → 点 `允许`；交付询问「选满意交付 → 点确认」。
  2. **见证看门狗**：监听会话 JSONL 中「✅ 已登记 N 项同会话真人见证」→ 立即 HTTP 助推 L1 输出 testing 标记（注意 urllib 超时 8s 太短，需 60s）。
  3. **直连 RPC**：`POST http://127.0.0.1:19877/send_message {"session_id","message"}` 可绕过 MCP 超时，秒级驱动。
  4. **交付标记**：ack 登记后注入 `<!-- PHASE_ADVANCE: delivered -->` 即刻推进（ack 绑定 report.runId，重跑 GWT 会使旧 ack 失效）。
- 关键教训：**ack 与 report runId 强绑定**。见证新鲜期内若重跑 GWT，ack 必须重新登记（新 runId）。

### P1-9 定时任务 MCP 工具缺 modelId，造成隐性 Sota 消耗
- 现象：`create_automation` / `update_automation` 不暴露 `modelId`，任务继承创建会话模型；本实例两条 E2E 监控任务（`5372ddf2` 运行 785 次、`e916ac02` 运行 930 次）长期以 GLM-5.3 每 25–30 分钟运行。
- 叠加因素：`sessionMode=reuse` + `lastSessionId` 会复用旧模型会话，只改 modelId 无效；`automation-manager.ts readIndex()` 有进程内缓存，改文件需重启实例生效。
- 建议：给 create/update 工具暴露 modelId；UI 显示任务模型；暂停/启用与模型变更分离并给出「重启后生效」提示。
