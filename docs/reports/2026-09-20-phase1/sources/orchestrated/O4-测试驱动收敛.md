### 五、驱动骨架与测试闭环规范改进建议

#### 建议 1：骨架②同源约束向 full 模式强制扩展

**问题**：US-03 在 R1–R4 全程 expected 含运行时值 `listbox_size`，即使 AC-F2 修好了 US-04，US-03 仍未修复。

**建议**：在 `driver-skeleton.py` 的 `make_check` 中，对 acceptance 模式（covers 非空）增加一条约束——若 `expected` 字符串中出现的数字字面量（如 `listbox_size: 2`）同时也是运行时会变化的变量名或返回值，骨架应报警（不是错误，而是 WARM-1 建议）。更严格方案：在 `engineering.json` 的 `covers` 字段中声明每个 storyId 对应的"不变属性"列表，骨架据此校验 expected 中是否意外嵌入了变量。

**形式化**：在 §5.3 五项自检中新增一条"⑥ expected 静态性检查"：acceptance 模式的 expected 应为编译期常量（无变量插值）；违反时输出 WARM-1（非 BLOCKER，由验收方决定是否接受），但不影响退出码。

#### 建议 2：storyId 正确性校验（覆盖 ① 的"非空"扩展到"正确"）

**问题**（DD-3）：`story_id_base = covers[0]` 导致 covers 乱序时 storyId 与 label 不一致（US-01 check 标上 US-05 的编号）。

**建议**：在 `engineering.json` 中声明每个 check 的正确 storyId（强约束），或在 `covers` 中声明期望的故事顺序（骨架据此校验 storyId 是否与 label 一一对应）。违反时输出 R2-WARN 而非 WARM-1（因为 storyId 错误比 expected 静态性偏差更严重）。

#### 建议 3：cli-driver 适配器的宿主协议豁免或升级

**问题**（DD-4）：`tests/test_history_store.py` 无 `checks[]`/`storyId`，无法按用户故事自动归因。

**建议**：在 `engineering.json` 的 adapter 类型中明确区分 `cli-driver`（无 stdin/stdout 协议）与 `native-driver`（有宿主协议），并对 `cli-driver` 提供等价归因字段（如把每条 pytest/断言转换为 `{storyId:null, label:"<test_name>", pass:<bool>}` 列表）。这样验收平台可以不依赖文件内容解析，直接按统一结构处理所有 adapter 类型。

#### 建议 4：验收标准脚本的自我验证（针对 E-1 教训）

**问题**：项目自带 `_stress_concurrent.sh` 声称 `switchinterval=1e-6`，实际以 5ms 运行（Banner 与条件不符），却 exit 0。

**建议**：在 desktop-app.md §5 测试闭环中增加一条"验收脚本自验证"规范：任何验收用脚本（压测、性能、fuzz）在声明其运行条件（如 `switchinterval=1e-6`）后，必须在产物中输出该条件的**实际生效值**（如"actual_switchinterval=0.005"）。若声称值与实际值不符，脚本应 exit 非零或输出 WARNING。这不是驱动骨架的职责，而是测试闭环规范（§5）的补充。

#### 建议 5：entry-point 覆盖作为契约测试前置条件

**问题**：F-1（entry-point ImportError）被驱动用包内导入绕过了，但 F-1 影响用户按文档启动。

**建议**：在 `engineering.json` 的 tests 数组中增加一项前置测试 `tst-entry-point`，命令为 `python3 src/main.py`（脚本模式），退出码要求 0（存活）或 124（timeout），不允许 1（ImportError/崩溃）。此测试在契约三条之前执行，其失败不计入产品缺陷，而计入"入口覆盖缺口"——将 F-1 这类"测试覆盖缺口伪装成产品缺陷"的情况制度性消灭。

### 六、一句话总结

> **"4 轮收敛（vs 基线 8 轮/5 盲修）、盲修率从 62.5% 压至 0%、骨架五项自检 4/5 在位驱动 error 透传与 evidence 落盘制度化——但 US-03 弱断言残留（DD-2 残留）、storyId 乱序误标（DD-3）、entry-point 覆盖缺口（F-1）被测试侧系统性发现并补位，证明测试驱动方法论已从'事后查漏'进化到'首轮即捕获'，本轮最有价值的方法论教训是：带验证脚本的验收标准必须同时核验脚本自身是否真的满足它声称的条件（E-1：threading.set_switchinterval 静默降级 vs 声称 1e-6）。"**
