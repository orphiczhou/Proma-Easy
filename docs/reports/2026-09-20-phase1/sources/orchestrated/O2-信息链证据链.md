### 二、平台机制改进建议（探测注入 / 凭证门禁 / 证据规范）

> 每条按「本次实证依据 → 建议动作 → 可否机器判定」给出，尽量做成可自动化的门禁项而不是文字要求。

#### A. 探测注入机制（根治 D-1 类）

1. **事实必须结构化 + 自带凭据**。当前注入是散文：`【本机环境事实】Linux (WSL2)…无 Docker…`，下游只能整段照抄或整段丢弃（本次是「照抄 1 条、丢弃 1 条」）。建议注入格式改为逐条记录：
   `{"key":"os.kernel","value":"6.8.0-139-generic","probe_cmd":"uname -a","probed_at":"…","source":"orchestrator"}`。
   *机器判定*：下游产物凡出现环境断言，须能映射到注入项的 `key`；无 `probe_cmd` 的注入项应带 `unverified:true` 标记。
2. **注入前自校验**。编排方在注入时执行一次 `probe_cmd` 与 `value` 对比，不一致则**标注 mismatch 并附双方值**，禁止静默下发。本次 2/4 条为假（内核/发行版、Docker），若注入项自带 `probe_cmd`，`uname -a` / `docker info` 会在**下发前**就矛盾暴露。
3. **产物侧「本机实测」门禁**。文档中出现「本机/实测/环境事实」等词并要求可信时，同段落须含 `probe_cmd` + `probed_at`，且该事实须存在于 `env_probe.json` 的组件集合内。本次 `env-manifest.md:3`「本机实测」+ `:9 WSL2` 在无对应组件（15 组件里没有 OS/内核）时本应被门禁拒绝。
4. **补齐 env_probe 组件**。至少新增 `os.kernel`(`uname -r`/`/proc/version`)、`os.distro`(`/etc/os-release`)、`container`(`/proc/1/cgroup` + `/proc/sys/fs/binfmt_misc/` 或 `systemd-detect-virt`)、`docker`(`docker info --format {{.ServerVersion}}`)——本次这四个全缺，正是 D-1 得以长期存活的结构原因；`scripts/check_env.sh` 同步（目前 `uname|/proc/version|docker` 零探测）。
5. **「被丢弃的注入事实」需留痕**。本次「无 Docker」既未进产物也未留任何「已核验为假」的记录；建议要求架构产物带一节 `注入项处置表`（accepted / rejected + 理由 + 凭据），使「无视」与「否证」可区分。

#### B. 凭证（裁决）门禁（根治 D-7 / D-8 / D-9）

1. **对抗审查产物强制落盘 + 结构化**。攻击者/防御者必须产出 `09_AUDIT/AC-attack-rN.json`、`AC-defense-rN.json`，字段：`finding_id / severity(red|yellow) / dimension / evidence(≥客观引用，含文件:行) / verdict / auditor_session_id / ts`。本次两个会话总计 0 次写盘，裁决全在会话内 →「终裁签收」在工程内不可自证。
   *机器判定*：签收门禁检查 `09_AUDIT/` 存在性与字段完备性；缺失即拒签。
2. **编号命名空间登记 + 引用校验**。任何被引用的编号（`F-n` / `AC-Fn` / `Yn`）须在工程内单一定义源（ID→描述→证据）；引用未登记编号 → 门禁 error。本次 `Y2/Y5/Y11` 零命中的根因就是攻击者报告未落盘、Y 命名空间随会话消失（D-9），导致测试方**无法按编号核验**、只能降级为「按可观测变更覆盖」。
3. **finding 处置映射表作为签收附件**。签收须附 `finding_id → 修复文件:行 → 复验报告路径 → 复验者会话 → 复验时间` 全表。本次 AC-F1/F2/F3 有此映射（三方独立复算，质量高），但攻击者的 Y1…Yn **无映射**，形成「已修但无法对账」的灰区。
4. **复算证据不得存放于 `/tmp`**。终裁的复算原始产物（变异体源、构造命令、原始 stdout/exit）须归档到工程（或工作区固定目录）并纳入签收清单；本次 `/tmp/{orig,mut}-08_APP`、`mut_out.json`、`f1_indep.py` 随时可被清理（D-8）。
5. **终裁简报需含观察员 findings**。本次终裁（攻击者→防御者）从未引用 O1–O4 报告；而 O2 连续两轮把 `env-manifest.md:9` 标红、O3 报告存在、时间上均早于终裁（O3 14:27、O2 14:33、O1 16:13）→ 建议平台在终裁 brief 中附「观察员红/黄项摘要」，使「终裁未捕获 D-1」可被避免（这是本次唯一红项得以存活到终裁的直接机制原因）。
6. **观察员发现应可升级为 finding**。给观察员一条「提交 finding 到 `09_AUDIT/findings-inbox.json`」的只读→仅追加通道，使其不需写工程目录也能进入裁决链（目前观察员只能写自己的报告，不进裁决）。

#### C. 证据规范（根治 D-2 / D-5 / D-10，缩小两套标准差异）

1. **统一证据 schema，禁止「仅打印」与「无时间戳落盘」**。推荐 `{ts_unix_ms, label, subject, expected, actual, verdict, reproducible_cmd?, artifacts?}`；spike 与 `08_APP` 使用同一规范（本次 spike 3/3 无 ts、`08_APP` 102/102 有 ts）。模版 `desktop-app.md:248,280` 已写明但**无门禁**，建议在 `driver-skeleton.py`/`probe.py` 模板里直接提供 `write_evidence()`，从源头保证。
2. **证据目录分层 + INDEX**。`evidence/rN/` + `INDEX.md`（时间、轮次、结论、被引用的 report）。本次 102 份同名族文件平铺，弱断言时代的 r1/r2 证据与终态真断言证据混存（靠文件名 ts 区分），审计成本高。
3. **禁止 expected 反填**。门禁检测 `expected` 是否来源于被测运行输出（自证式证据）；本次 US-04 已闭环（真断言 + 变异体实证），US-03 `listbox_size` 仍反填（D-10）——**该门禁能把「测试通过」与「测试有鉴别力」分开**。
4. **「声称条件」必须与实际生效值对账**（E-1 类，本次最有价值的方法论教训）：脚本 banner / README 中声称的运行参数，须在运行时读回并断言（如 `sys.getswitchinterval()`），不一致即非零退出。建议在骨架提供 `assert_effective(claimed, actual)` 工具；本次「声称 1e-6、实际 5ms、exit 0」正是缺少此对账。
5. **变异/反事实验证须归档四件套**：变异点（文件:行 + diff）、构造命令、原始输出（含 exit code）、预期失败集合。本次 F-2 的变异设计极佳（攻击者指出场景失效 → 测试方/防御者两套独立变异体），但产物在 `/tmp` 且无落盘的变异记录。
6. **交付前「文档状态一致性」门禁**：根 `README.md` 的阶段状态/产物状态表须与终态一致（本次 `:4`/`:20`/`:21` 仍为「待接手/⏳」，与终裁矛盾，D-11）；同时校验「文档内承诺」与「实现」的对应（AC-F3 修复前 `README.md:131` 承诺 vs 实现的矛盾，是攻击者靠人工比对发现的，建议做成模板化的「承诺→实现」清单）。
7. **探测时间戳不可缺**（D-1 附带问题）：`env-manifest.md` 声称「本机实测」却无探测时间；任何「实测/快照」类产物建议强制 `probed_at`（工具注入，无则拒收）。

### 三、一句话总结

**本次工程的信息链在「实验→证据→结论→修复复验」方向上是可复算、可回溯的高质量链（probe 死锁被资产化、AC-F1/F2/F3 经三方独立复算与变异体鉴别力实证、开发段 102 份证据 100% 带时间戳），但在「裁决→签收→交付」方向上是断的：AC 攻击者/防御者的裁决报告零落盘、编号引用成孤儿（Y2/Y5/Y11 零命中）、注入失真「OS=WSL2」在无任何凭据的「本机实测」表格里存活到终裁、交付文档仍含「声称 1e-6 实际 5ms」的自述失真与过期的入口状态表——即证据质量优秀、裁决与交付的可审计性不合格，建议平台优先补上三件事：注入事实结构化+自校验的探测门禁、对抗裁决强制落盘与编号登记门禁、统一证据 schema 与「声称条件对账」门禁。**
