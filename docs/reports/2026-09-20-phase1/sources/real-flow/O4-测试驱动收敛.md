### 二、驱动骨架五项自检观察

**结论：驱动未基于 v127 `driver_skeleton.py`——是自定义实现（2811 行 `run_driver.py`），但五项自检机制在驱动代码内** **概念性实现**，不等同于骨架文件导入。**

| # | 自检项 | 骨架要求 | 驱动实现方式 | 在位判定 |
|---|--------|---------|------------|---------|
| ① | storyId 非空校验 | `make_check` 拒绝 acceptance 模式 covers 非空时空 storyId | **有**：`result.add(storyId, ...)` 传入 storyId，非空由调用方保证；无骨架级强制拦截 | ⚠️ **概念性实现，无强制拦截** |
| ② | expected/actual 同源 | `assert_same_source(expected_const, probe_fn)` 强制 actual 来自 probe | **有**：`clip_write` / `clip_read` / `xdotool` 系统侧探测写入，actual 来自真实执行结果；无 `assert_same_source` 但语义同源 | ⚠️ **概念性实现（无函数级强制）** |
| ③ | 输出 JSON schema 校验+退出码表 | `emit_result` 自校验后 stdout 单 JSON | **有**：`Result.to_dict()` 输出 `{"testId","target","checks"}`；退出码约定 0/1/2 三档 | ✅ **在位** |
| ④ | 顶层异常包裹 | `run_guarded` 的 `except BaseException` 含 SystemExit | **部分**：主流程 `try/except` 包裹，`run()` 函数返回 None 代替异常；无统一 `except BaseException` 全局包裹 | ⚠️ **部分在位** |
| ⑤ | 环境前置自检 | `check_environment()` 检查 REQUIRED_DISPLAY | **有**：`DISPLAY` 环境变量检查在 `Product.start()` 前；`XDG_DATA_HOME` 隔离工作区 | ✅ **在位** |

**v127 骨架 vs 自定义驱动对比**：

| 维度 | v127 骨架（编排版） | 自定义驱动（本工程） |
|------|------------------|------------------|
| 文件来源 | `driver_skeleton.py` 模板复制到 `drivers/` | 手写 2811 行，无模板文件 |
| 五项自检 | **显式导入**，骨架函数级强制 | **概念性实现**，依赖驱动代码质量 |
| ② 同源强制 | `assert_same_source()` 强制 probe 函数 | 语义同源但无函数级强制 |
| ④ 异常包裹 | `run_guarded()` 全局统一 | `try/except` 分散，无统一 `except BaseException` |
| AC 审查覆盖 | 由 AC 审计补充发现 DD-1~4 | AC R1~R3 全程覆盖，4 red 全部关闭 |

**推断**：本工程以"更重的自定义驱动"换取"更强的 AC 审查覆盖"——驱动本身质量更高（2811 行 vs 编排版 ~300 行），但五项自检无骨架级强制约束。

### 七、改进建议

#### 建议 1：自定义驱动与骨架文件明确隔离

**问题**：本工程 2811 行自定义驱动质量高，但与 v127 `driver_skeleton.py` 五项自检机制的"概念性实现"语义不等价——无函数级强制约束，依赖驱动代码质量。

**建议**：在 `engineering.json` 中明确声明驱动类型（`custom-native-driver` vs `skeleton-based-driver`），对 `custom-native-driver` 要求 AC 审查覆盖五项自检机制（已由本工程 AC 审计实践验证可行）。

#### 建议 2：AC 审查报告结构化归档

**问题**：`ac-verdict.json` 存在于 coding 阶段会话子目录和 08_APP，不在 06_TESTS；平台侧无统一归档路径。

**建议**：在 `engineering.json tests[]` 增加 `auditVerdict` 字段引用 `ac-verdict.json` 路径；或在 06_TESTS 建立 `AUDIT/` 子目录统一归档 AC 报告。

#### 建议 3：06_TESTS 与 workspace 会话子目录双写机制

**问题**：当前测试证据在 workspace 会话子目录（`ba3557bb-.../evidence-08app/`），06_TESTS 为空——平台侧验收报告与工程目录分离。

**建议**：工程交付时测试侧应将证据归档到 06_TESTS/evidence/，workspace 会话子目录仅作中间缓存。

#### 建议 4：v127 坑库回填阈值与 AC 审查等效认定

**问题**：本工程 3 轮 AC 审查未触发 >3 轮复盘机制，但 AC 审查已起到等价覆盖效果。

**建议**：在 `engineering.json` 或平台配置中明确"AC 审查轮次可计入收敛轮次"——即 AC R1+R2+R3 应计入"验收轮次"，使 >3 轮触发条件在 AC 覆盖场景下提前生效。

#### 建议 5：entry-point 前置测试制度化（跨工程建议）

**问题**（来自编排版 F-1 教训）：驱动用包内导入绕过脚本模式 entry-point，契约测试全绿但 entry-point 无法按文档启动。

**建议**：engineering.json 增加 `tst-entry-point` 前置测试，命令为 `python3 <entry>`（脚本模式），退出码要求 0 或 124，不允许 1。
