## 二、关键架构决策落地

以下5项关键决策从探索报告进入架构文档并细化为可执行方案：

### 决策1：MVP串行角色切换

**决策**：需求分析师→UI/UX顾问→架构设计师→工程经理，串行切换。
**实现**：Session Restart + Context Backfill，~9h改动量（放弃并行方案的30h）。
**位置**：architecture.md §5, agent-role-switch.seq.puml

### 决策2：沙箱L0文件隔离 + L1进程限制

**决策**：项目目录即边界，子进程cwd=项目目录，资源限制。
**否决**：Docker（安装门槛）、WebContainer（无Python）、iframe（能力不足）。
**位置**：architecture.md §6

### 决策3：点选纠错data-ai-id主路径

**决策**：Phase 1用data-ai-id标注，Phase 2加截图+视觉模型兜底。
**位置**：architecture.md §7, click-to-fix-report.md

### 决策4：技术组件零依赖选型

**决策**：PlantUML用LLM原生理解+GWT用Agent原生执行器+快照用fs.linkSync+埋点用JSONL追加。
**位置**：architecture.md §1, A3报告

### 决策5：模型-角色映射

| 角色 | 模型 | 验证来源 |
|------|------|---------|
| 需求分析师 | deepseek-v4-flash | 对话流畅，1M上下文 |
| UI/UX顾问 | MiniMax 2.7/M3 | C2：6原型审查通过 |
| 架构设计师 | deepseek-v4-pro | 强推理，PlantUML生成 |
| 工程经理 | deepseek-v4-pro | SOTA长上下文 |
| 全栈开发/测试 | GLM 5.1 | C1：端到端5/5通过 |
| 裁判Agent | deepseek-v4-flash | 快速判定，低成本 |

## 四、PlantUML约束体系

### 类图覆盖（5域22类）

```
前端UI层    → AppShell + 6页面组件
向导Agent   → GuideAgent + 4角色类 + SessionRouter
编程Agent   → CodingAgent + TestAgent + ReviewerAgent + PM
裁判Agent   → JudgeAgent + HardConstraintChecker + SoftConstraintEvaluator
基础设施    → SnapshotManager + TelemetryCollector + SandboxManager + ProjectDocumentSystem
```

### 时序图覆盖（5流程）

| SEQ | 流程 | 关键覆盖 |
|-----|------|---------|
| SEQ-1 | 用户创建项目 | 模式选择→需求对话→PRD确认→原型→架构 |
| SEQ-2 | Agent角色切换 | Session Restart→Context Backfill→角色加载 |
| SEQ-3 | 代码生成循环 | 读PlantUML→生成→自修复→GWT测试 |
| SEQ-4 | 裁判审查 | 硬约束逐项检查→软约束评估→综合判定 |
| SEQ-5 | 异常熔断 | 3次修复→熔断→回滚→用户通知 |

所有时序图参与者与类图100%一致，可供裁判Agent做代码结构校验。

## 五、数据模型

5个实体覆盖全部持久化需求，字段总数32个，存储方案为JSONL/文件系统。

| 实体 | 核心字段 | 用途 |
|------|---------|------|
| Project | projectId, mode, template, status, currentStage | 项目管理 |
| Snapshot | snapshotId, projectId, triggerType, description | 线性回滚（无分支） |
| TelemetryEvent | eventId, eventType(13种), payload | 全量科研埋点 |
| SessionContext | currentStage, currentRole, conversationSummary | 上下文恢复 |
| DocumentMeta | docPath, docType, version, status | 裁判Agent文档追踪 |
