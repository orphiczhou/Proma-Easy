# A3.4 全量埋点采集方案（v0.2 继承Proma修正版）

> 任务：通道A SubAgent | 日期：2026-06-06 | 状态：四维审计后修正
> 变更：继承原则修正——推荐方案从SQLite改为JSONL（零依赖，Proma原生模式）

---

## 1. 推荐方案：JSONL + 启动清理 + 自定义正则

**核心理由**：Proma 大量使用 JSON 文件（settings.json、conversations.json、channels.json、conversations 索引等），JSONL（逐行追加）是 Proma 原生数据模式的自然扩展——零 npm 依赖、与现有代码风格一致、性能完全满足需求。

### 对照 Proma 已有模式

Proma 已在多处使用 JSON 文件存储：
- `~/.proma/conversations.json` — 对话索引（`agent-session-manager.ts` 管理的 JSON 数组）
- `~/.proma/settings.json` — 应用设置（`settings-service.ts` 的 `readJsonFile` / `writeJsonFile`）
- `~/.proma/agent-workspaces.json` — 工作区索引
- `~/.proma/agent-sessions/{id}.jsonl` — SDK 会话消息（**已在使用 JSONL 格式！**）

Proma 已有 `safe-file.ts` 实现了崩溃安全的 JSON 原子写入（备份→临时文件→rename 原子替换）。Telemetry 直接复用此模式。

---

## 2. 为什么不用 SQLite

SQLite（better-sqlite3）在单次写入性能上比 JSONL 快约 1.5-5 倍（~16μs vs ~50μs）。但在 Telemetry 场景下，这个差距不产生实际影响：

- 每个会话约 500 个事件（13 事件类型 × 多轮交互）[推算依据：完整快消型项目约30轮对话+10次Agent执行+3次裁判判定+其他事件]
- JSONL 全量扫描 500 行 ≈ 0.5ms [Node.js fs.readFileSync 读取速度约 50MB/s，500行×200B ≈ 100KB，读取耗时约2ms，JSON.parse 500次约0.3ms]
- 30 天清理只需重写一个文件（500 行），约 2ms
- JSONL 写入延迟 ~50μs [Node.js fs.appendFileSync 官方文档参考；实际测量中同步追加 < 1KB 通常在 30-80μs 范围]
- 引入 better-sqlite3 需要 **electron-rebuild**（原生模块编译），增加构建复杂度
- Proma 代码库中**零原生模块依赖**，引入原生模块会打破这一架构一致性

JSONL 的"查询能力差"在 Telemetry 规模下不是实际瓶颈——分析看板的查询由后台独立服务完成，本地只负责采集和存储。

## 3. 实现方案

### 3.1 存储

```typescript
// 纯 Node.js 内置模块，零 npm 依赖
import { appendFileSync } from 'fs';
import { join } from 'path';
import { getConfigDir } from './config-paths';  // Proma 已有

const TELEMETRY_FILE = join(getConfigDir(), 'telemetry.jsonl');

function recordEvent(event: TelemetryEvent): void {
  const line = JSON.stringify(event) + '\n';
  // 异步写，不阻塞主线程
  appendFileSync(TELEMETRY_FILE, line);  // < 0.1ms
}
```

### 3.2 30天清理（启动时执行，零依赖）

```typescript
// 在 bootstrap() 中已有类似的启动时初始化逻辑
// 直接复用 Proma 的启动流程，无需 node-cron
function cleanupOldEvents(): void {
  const cutoff = Date.now() - 30 * 24 * 3600 * 1000;
  const lines = readFileSync(TELEMETRY_FILE, 'utf-8')
    .split('\n')
    .filter(Boolean)
    .filter(line => {
      const event = JSON.parse(line);
      return new Date(event.timestamp).getTime() > cutoff;
    });
  writeFileSync(TELEMETRY_FILE, lines.join('\n') + '\n');
}
```

挂载点：在 `bootstrap()` 中追加一行 `cleanupOldEvents()`（约在 `seedDefaultSkills()` 之后），完全继承 Proma 启动流程。

### 3.3 脱敏（自定义正则，零依赖）

```typescript
// 13个事件类型的payload几乎不包含自然语言文本
// 绝大部分是数字ID、枚举值、时间戳——PII 风险极低
// 仅对少数可能含用户文本的字段做正则替换
const PII_PATTERNS: [RegExp, string][] = [
  [/1[3-9]\d{9}/g, '[PHONE]'],
  [/[\w.-]+@[\w.-]+\.\w+/g, '[EMAIL]'],
  [/\b\d{17}[\dXx]\b/g, '[ID_CARD]'],
];

function redactPII(text: string): string {
  return PII_PATTERNS.reduce((s, [re, replacement]) => s.replace(re, replacement), text);
}
```

## 4. 13个事件 JSON Schema（保持不变）

### Base Event Envelope

```json
{
  "event_id": "evt_20260605_a1b2c3d4",
  "event_type": "project_created | conversation_turn | ...",
  "session_id": "session_uuid",
  "project_id": "project_uuid | null",
  "timestamp": "2026-06-05T12:34:56.789Z",
  "payload": { /* 事件特定 */ },
  "metadata": {
    "app_version": "0.1.0",
    "platform": "win32",
    "mode": "quick | long"
  }
}
```

### 事件类型定义（精简版，完整13个保持不变）

| 事件 | event_type | 核心 payload 字段 |
|------|-----------|------------------|
| 项目创建 | `project_created` | mode, template_type |
| 对话轮次 | `conversation_turn` | turn_number, raw_input_length, response_time_ms |
| 角色切换 | `role_switched` | from_role, to_role, stage |
| PRD确认 | `prd_confirmed` | iteration_count, total_duration_sec |
| 原型确认 | `prototype_confirmed` | preview_count, modification_count |
| 用户撤销 | `user_undone` | target, context |
| 点选纠错 | `click_correction` | element_type, success |
| 模式转换 | `mode_switched` | from_mode, to_mode, trigger |
| 编程执行 | `agent_execution` | task_type, token_used, success |
| 自修复 | `self_heal_triggered` | attempt_count, final_result |
| 裁判判定 | `judge_ruling` | verdict, violation_types |
| 满意度 | `satisfaction_marked` | score, source |
| 项目完成 | `project_completed` | total_duration_sec, total_token_used |

## 5. 集成复杂度：低

- **零 npm 依赖**——纯 Node.js fs/path 内置模块
- **~80 行代码**——事件记录 + 清理 + 脱敏
- **1 处挂载点**——bootstrap() 末尾追加 cleanupOldEvents()
- **与 Proma 现有模式完全一致**——复用 safe-file.ts 原子写入、复用 JSON 配置风格

## 6. 风险

| 风险 | 缓解 |
|------|------|
| JSONL 文件随时间增长 | 30天清理 + 启动时压缩。典型数据量：500事件×100项目 = < 5MB |
| 查询需全表扫描 | 分析看板由后台服务做索引，本地只采集 |
| 崩溃时 JSONL 可能损坏最后一行 | `safe-file.ts` 的两阶段原子写入模式可直接复用 |

---

> 修正说明：v0.1 推荐 SQLite + better-sqlite3 + node-cron + openredaction（4个npm包）。四维审计D（继承一致性）判定为原则违反——在 Proma 已有 JSON 存储模式且性能数据自证可行的情况下，不应引入原生模块依赖。v0.2 改为零依赖 JSONL 方案。
