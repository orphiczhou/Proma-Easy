## 1. 问题概述

在 Node.js/TypeScript 环境下，解析 `.puml` 文件（PlantUML 类图和时序图），提取类结构信息，并与编程 Agent 产出的 TypeScript 代码进行结构一致性校验。该能力服务于 PRD v0.2 §8 定义的 PlantUML 强约束层——裁判 Agent 通过此能力校验代码结构是否与设计规约一致。

**设计前提（证据来源：A1.1 目录结构探查报告，2026-06-05）：**
- **TypeScript 全栈**：A1.1 §技术栈关键词确认 Proma 使用 TypeScript 5.x 全栈，`typescript` 包已存在于 monorepo 依赖中（通过 `package.json` 声明，Bun workspace 管理）
- **LLM 适配器已就绪**：A1.1 确认 `packages/core/`（`@proma/core`）封装了 `lib/adapters/` 三层 LLM 提供者——Anthropic Claude Agent SDK、Google Gemini、OpenAI。Agent 引擎核心位于 `apps/electron/src/main/agent-*.ts`，集成在 `apps/electron/src/main/lib/adapters/`。PUML 理解可直接复用这些适配器，零新依赖
- **Mermaid 渲染组件已存在**：A1.1 确认 `packages/ui/src/mermaid-block/` 是现成的 Mermaid 图表渲染组件，可通过 UVue/React 组件直接嵌入
- **纯 JS/TS 生态**：A1.1 确认 Proma 为 "Hybrid Electron 桌面应用 — 纯 Bun monorepo"，无 Java 运行时
- 目标工程遵循"能用文件就别用数据库，能用内存就别用 Redis，能用函数调用就别用消息队列"原则

## 2. 调查项一：PlantUML 解析（类结构理解）

### 2.1 候选方案

| 方案 | 类型 | 优点 | 缺点 |
|------|------|------|------|
| **LLM/Agent 原生理解**（推荐主力） | Prompt 工程 + Proma LLM 适配器 | 零新依赖；完全理解任意 UML 语法（类图/时序图/状态图）；可自适应 PUML 语法变体；平台自洽（Agent 平台用 Agent 理解） | 需设计稳定的提取 Prompt；LLM 输出可能有非确定性；长文本 Token 开销 |
| **plantuml-parser** (dntzhang/org-408, 备选) | npm 包 ~0.4.x | TS 类型完备；支持 class/component/usecase 图；输出含 name/members/extends_/implements_/generics/relationships；PEG.js 解析 | 未正式发布 1.0；members 解析不完整；不支持 sequence 图；维护节奏慢 |
| **plantuml-parser** (Enteee, npm 1.x, 备选) | npm 包 1.x | MIT 许可证 | 与 dntzhang 版本有 fork 关系，功能相似；同样不支持完整时序图 |
| **自定义 PEG.js/ANTLR 语法** | 自研解析器 | 完全可控；可按需求定制 | 开发成本高（数人周）；PlantUML 语法边界情况多；需额外引入 PEG.js/ANTLR 运行时 |

**已排除方案：**
- ~~Node.js 子进程调用 PlantUML JAR~~：需要 Java 运行时，与 Proma 纯 JS 生态冲突（违反继承原则）
- ~~plantuml-encoder~~：引入 Java 依赖链

### 2.2 推荐方案：**LLM/Agent 原生理解**（主力）+ **plantuml-parser**（备选）

#### 主力方案：LLM 原生理解

**理由：**
- Proma 平台的本质是 Agent 编程平台——向导 Agent 本身就具备强大的自然语言理解和结构化提取能力。A1.1 报告确认 Proma 的 LLM 适配器位于 `packages/core/src/lib/adapters/`（Anthropic / Gemini / OpenAI 三层），Agent 引擎核心在 `apps/electron/src/main/agent-*.ts`。这些模块可直接用于 PUML 文本的结构化理解，零新依赖
- 让向导 Agent 直接读取 `.puml` 文本文件，通过结构化 Prompt 提取类名、方法、属性、关系等，是零额外依赖、与平台哲学完全一致的做法
- PRD v0.2 §8 已明确"裁判 Agent 可直接解析文本进行代码结构校验"，LLM 解析完全符合此设计意图——裁判 Agent 本身就是运行在 Proma Agent 引擎上的一个 Agent 角色
- 相比第三方 parser，LLM 原生理解不受语法版本限制，可同时处理类图和时序图。且 Proma 已内置三种 LLM 提供者，可在成本/质量间灵活选择（Gemini 处理批量提取，Claude/OpenAI 处理高精度需求）

**Prompt 设计示意（注入向导 Agent System Prompt）：**

```typescript
// 单次调用的结构化提取 Prompt
const extractPrompt = `
请从以下 PlantUML 代码中提取类结构信息，以 JSON 格式输出。

\`\`\`plantuml
${pumlContent}
\`\`\`

要求提取：
1. 每个类的 name, isAbstract, members(含 name, type, visibility, isStatic, isMethod)
2. 继承关系（extends\_ 和 implements\_）
3. 类间关系（关联、聚合、组合、依赖）的 left, right, 箭头类型
4. 泛型参数

输出格式：
{
  "classes": [...],
  "relationships": [...]
}
`;
```

#### 备选方案：plantuml-parser（降级策略）

当 LLM 提取结果需要交叉验证，或对结构化确定性有更高要求时，使用 plantuml-parser 做第二道解析。

## 3. 调查项二：TypeScript 代码结构提取

### 3.1 候选方案

| 方案 | 来源 | 优点 | 缺点 |
|------|------|------|------|
| **TypeScript Compiler API**（推荐） | `typescript`（已存在于 Proma） | **零额外 npm 包**；官方支持；完整 AST 信息；可精确控制提取粒度 | API 底层且较冗长；需自行处理类型推导和关系遍历 |
| **ts-morph** | `ts-morph` 28.x | 高封装度；提供 `getClasses()`/`getMethods()`/`getProperties()`/`getStructure()`；API 简洁 | 增加一个 npm 依赖；对简单场景可能过重；Pro ma 已有 TypeScript 依赖，ts-morph 缺乏必要性证据 |

### 3.2 推荐方案：**TypeScript Compiler API**

**理由：**
- **零新增依赖**：A1.1 报告确认 Proma 使用 "TypeScript 5.x 全栈" 作为核心语言，`typescript` 编译器包必然存在于 Proma monorepo 根 `package.json` 或 `packages/core/package.json` 的 dependencies/devDependencies 中。直接使用其 Compiler API 无需安装任何额外包
- 直接使用 `typescript` 包自带的 Compiler API（`ts.createSourceFile()`, `ts.createProgram()` 等），功能完备且官方维护。Compiler API 是 TypeScript 编译器本身的组成部分，不是独立第三方库，与 Proma 的 TypeScript 版本自动保持兼容
- 虽然在简单提取场景比 ts-morph 需要更多样板代码，但本次需求的提取逻辑本身就是定制化的，样板代码是一次性成本。且提取逻辑可封装为 `packages/shared/src/code-extractor.ts` 供团队复用
- 遵循"非必要不引入新组件"的继承原则——ts-morph 作为 TypeScript Compiler API 的高封装包装器，在已有 TypeScript 依赖的情况下缺乏引入必要性

**提取示例：**

```typescript
import * as ts from "typescript";
import * as fs from "fs";
import * as path from "path";

interface ExtractedClass {
  name: string;
  isAbstract: boolean;
  properties: Array<{ name: string; type: string; isStatic: boolean }>;
  methods: Array<{
    name: string;
    parameters: Array<{ name: string; type: string }>;
    returnType: string;
  }>;
  extends: string[];
  implements: string[];
}

function extractClasses(sourceFile: ts.SourceFile): ExtractedClass[] {
  const classes: ExtractedClass[] = [];

  function visit(node: ts.Node) {
    if (ts.isClassDeclaration(node) && node.name) {
      const cls: ExtractedClass = {
        name: node.name.text,
        isAbstract: !!(node.modifiers?.find(m => m.kind === ts.SyntaxKind.AbstractKeyword)),
        properties: [],
        methods: [],
        extends: [],
        implements: [],
      };

      // 提取父类
      if (node.heritageClauses) {
        for (const clause of node.heritageClauses) {
          for (const type of clause.types) {
            if (clause.token === ts.SyntaxKind.ExtendsKeyword) {
              cls.extends.push(type.expression.getText(sourceFile));
            } else if (clause.token === ts.SyntaxKind.ImplementsKeyword) {
              cls.implements.push(type.expression.getText(sourceFile));
            }
          }
        }
      }

      // 遍历成员
      node.members.forEach(member => {
        if (ts.isPropertyDeclaration(member) && member.name) {
          cls.properties.push({
            name: member.name.getText(sourceFile),
            type: member.type ? member.type.getText(sourceFile) : "any",
            isStatic: !!(member.modifiers?.find(m => m.kind === ts.SyntaxKind.StaticKeyword)),
          });
        } else if (ts.isMethodDeclaration(member) && member.name) {
          cls.methods.push({
            name: member.name.getText(sourceFile),
            parameters: member.parameters.map(p => ({
              name: p.name.getText(sourceFile),
              type: p.type ? p.type.getText(sourceFile) : "any",
            })),
            returnType: member.type ? member.type.getText(sourceFile) : "void",
          });
        }
      });

      classes.push(cls);
    }
    ts.forEachChild(node, visit);
  }

  visit(sourceFile);
  return classes;
}

// 使用示例
const sourceCode = fs.readFileSync("src/model.ts", "utf-8");
const sourceFile = ts.createSourceFile(
  "model.ts",
  sourceCode,
  ts.ScriptTarget.Latest,
  true
);
const extractedClasses = extractClasses(sourceFile);
```

### 3.3 补充说明

- 若发现 Compiler API 使用场景中大量重复样板代码，可提取为 `packages/shared/` 中的 `code-extractor.ts` 工具函数，实现团队内复用
- 在 Proma monorepo 中，代码提取工具可放在 `packages/shared/src/` 或新增 `packages/core/` 模块，不需要独立 npm 包

## 4. 调查项三：对比逻辑（ClassComparator）

### 4.1 整体架构

```text
PUML 文件 (.puml)          TS 源代码 (.ts)
       |                           |
       v                           v
 LLM 原生理解               TypeScript Compiler API
 (备选: plantuml-parser)          |
       |                           v
       v                   TsClassDescriptor[]
 PumlClassDescriptor[]
       |                           |
       +----------+----------------+
                  |
                  v
          ClassComparator
          (纯 Node.js, 零依赖)
                  |
                  v
          DiffResult[]
```

### 4.2 对比维度与复杂度

| 对比维度 | PUML 输入 | AST 输入 | 复杂度 | 备注 |
|----------|-----------|----------|--------|------|
| **类存在性** | `element.name` | `cls.name`（Compiler API） | 低 | 按名匹配, 检测缺失/多余类 |
| **方法签名** | `member`（含 name, type 等） | `method.name`, 参数列表, 返回类型 | 中 | 需要考虑方法重载、泛型 |
| **属性字段** | `member`（字段） | `prop.name`, `prop.type` | 中 | 类型文本需要标准化后比对 |
| **继承关系** | `extends_[]` | `cls.extends` + `cls.implements` | 低 | 注意 extends 与 implements 的区分 |
| **关联/聚合** | `Relationship[]`（箭头类型 + 多重性） | 属性类型引用 + 泛型参数 | 高 | PUML 关系需要映射到代码中类型引用；需要跨文件分析 |
| **可见性** | `+`/`#`/`-`/`~` 前缀 | compilerFlags 中的可见性修饰符 | 低 | 符号映射直接 |

### 4.3 推荐方案：**纯自定义结构化对比**（零 npm 依赖）

**理由：**
- PlantUML 与代码 AST 的结构字段名和粒度不同，通用 diff 库无法直接处理语义映射
- **对比策略不只是一对一字段匹配, 还要处理以下语义差异：**
  - PUML 可能只描述 public 接口, 不描述 private 方法
  - PUML 的泛型约束可能与代码实现不完全一致
  - 代码中可能包含工具方法, 在 PUML 中没有建模
- 纯 Node.js 实现，零新增 npm 依赖（不引入 `@fry69/deep-diff` 等通用 diff 包）
- 建议将对比操作设计为**可配置的规则引擎**：
  - `exactMatch` 模式: 严格要求与 PUML 完全一致
  - `subsetMatch` 模式: 代码是 PUML 的超集即可（PUML 只关注契约）
  - `ignorePatterns` 模式: 忽略特定方法/属性

**非依赖自定义方案：**
- 不使用 `@fry69/deep-diff`：通用对象深比对无法处理 PUML 与 AST 间的语义映射差异，纯自定义能更精确控制比对逻辑，且不引入外部包

**自定义 Comparator 结构示意：**

```typescript
// 纯 Node.js，零外部依赖
interface CompareOptions {
  mode: 'exact' | 'subset';
  ignorePatterns?: RegExp[];
}

interface DiffItem {
  type: 'MISSING_CLASS' | 'EXTRA_CLASS' | 'MISSING_METHOD'
      | 'EXTRA_METHOD' | 'METHOD_SIGNATURE_MISMATCH'
      | 'MISSING_PROPERTY' | 'EXTRA_PROPERTY'
      | 'RELATIONSHIP_MISMATCH';
  className: string;
  detail: string;
  expected?: any;
  actual?: any;
}

class ClassComparator {
  compare(
    pumlClasses: PumlClassDescriptor[],
    tsClasses: ExtractedClass[],
    pumlRelations: PumlRelationship[],
    options: CompareOptions
  ): DiffItem[] {
    const diffs: DiffItem[] = [];
    const pumlMap = new Map(pumlClasses.map(c => [c.name, c]));
    const tsMap = new Map(tsClasses.map(c => [c.name, c]));

    // 检查 PUML 中的类是否在代码中存在
    for (const [name, pumlCls] of pumlMap) {
      const tsCls = tsMap.get(name);
      if (!tsCls) {
        diffs.push({ type: 'MISSING_CLASS', className: name, detail: `类 "${name}" 在代码中不存在` });
        continue;
      }
      // 检查方法、属性、继承关系...
    }

    // 检查代码中多余的类（subset 模式下忽略）
    if (options.mode === 'exact') {
      for (const [name] of tsMap) {
        if (!pumlMap.has(name)) {
          diffs.push({ type: 'EXTRA_CLASS', className: name, detail: `代码中多出了类 "${name}"` });
        }
      }
    }

    return diffs;
  }
}
```

### 4.4 与裁判 Agent 的集成

PRD v0.2 §8.4 定义裁判 Agent 的校验逻辑：读取代码 → 提取实际类结构 → 与 PlantUML 规约逐项对比 → 输出合规报告。本模块即为该逻辑的核心实现：

```
裁判 Agent 触发校验
       │
       ▼
读取 .puml 文件 → PumlExtractor.extract() → PumlClassDescriptor[]
       │
       ▼
读取 .ts 源文件 → TypeScript Compiler API → ExtractedClass[]
       │
       ▼
ClassComparator.compare() → DiffResult[]
       │
       ▼
裁判 Agent 判定通过/退回
```

## 5. 调查项四：渲染方案（可选，面向开发调试场景）

### 5.1 候选方案

| 方案 | 如何工作 | 优点 | 缺点 |
|------|----------|------|------|
| **Proma Mermaid 组件复用**（推荐主力） | PUML → Mermaid 语法转换 → 复用 `packages/ui/src/mermaid-block/` 组件渲染 | **零新依赖**；复用已有渲染管线；保持 UI 一致性；纯前端渲染无服务端开销 | 需要 PUML→Mermaid 语法转换逻辑 |
| **Pintora** | `@pintora/standalone` npm 包，纯 JS 渲染文本化图表 | 纯 JS/TS 生态；语法与 PUML 类似；无需转换 | 引入新 npm 包；需评估与 Proma UI 组件的集成成本 |
| **Mermaid.js 直接渲染** | `mermaid` npm 包，复用 Proma 现有 mermaid 但重新集成 | 社区成熟；官方维护 | Proma 已集成 Mermaid，直接复用 `mermaid-block` 组件即可；若另起炉灶则重复 |

**已排除方案：**
- ~~plantuml-encoder + PlantUML 在线服务~~：依赖网络和外部服务，引入 Java 依赖链
- ~~node-plantuml（子进程调用 JAR）~~：需要 Java + Graphviz 本地环境，与 Proma 纯 JS 生态冲突
- ~~self-hosted PlantUML 服务器（Docker）~~：需要 Docker 运行环境，增加部署复杂度

### 5.2 推荐方案：**Proma Mermaid 组件复用**

**理由：**
- Proma 已有现成的 Mermaid 渲染管线：`packages/ui/src/mermaid-block/`（详见 A1.1 目录结构）
- PlantUML 类图与 Mermaid 类图语法结构相似，可编写轻量转换器实现 PUML → Mermaid 语法映射
- 零新增 npm 包，零新增运行时依赖，完全复用现有 UI 组件
- 纯前端渲染，无服务端开销，无 Java 依赖

**PUML→Mermaid 转换示意：**

```typescript
// 轻量转换函数（纯字符串处理，零依赖）
function pumlToMermaid(pumlContent: string): string {
  const lines = pumlContent.split('\n');
  const mermaidLines: string[] = ['classDiagram'];

  for (const line of lines) {
    // 提取类声明: class ClassName { → class ClassName
    const classMatch = line.match(/^\s*class\s+(\w+)/);
    if (classMatch) {
      mermaidLines.push(`  class ${classMatch[1]} {`);
      continue;
    }

    // 提取属性: +field: Type → +field Type
    const fieldMatch = line.match(/^\s*([+#~-]?)\s*(\w+)\s*:\s*(\w+)/);
    if (fieldMatch && !line.includes('(')) {
      const [_, vis, name, type] = fieldMatch;
      mermaidLines.push(`    ${vis}${name} ${type}`);
      continue;
    }

    // 提取方法: +method(): Type → +method() Type
    const methodMatch = line.match(/^\s*([+#~-]?)\s*(\w+\(.*?\))\s*:\s*(\w+)/);
    if (methodMatch) {
      const [_, vis, method, returnType] = methodMatch;
      mermaidLines.push(`    ${vis}${method} ${returnType}`);
      continue;
    }

    // 提取关系: Class1 "1" -- "*" Class2 → Class1 --> Class2
    const relMatch = line.match(/(\w+)\s+"[^"]*"\s*(-[-\*]|\.\.)\s*"[^"]*"\s*(\w+)/);
    if (relMatch) {
      mermaidLines.push(`  ${relMatch[1]} --> ${relMatch[3]}`);
      continue;
    }

    // 提取继承: class Class1 extends Class2 → Class1 --|> Class2
    const extMatch = line.match(/^class\s+(\w+)\s+extends\s+(\w+)/);
    if (extMatch) {
      mermaidLines.push(`  ${extMatch[2]} <|-- ${extMatch[1]}`);
      continue;
    }
  }

  return mermaidLines.join('\n');
}
```

> **注：** 渲染方案是可选能力，服务于开发调试（架构师在可视化界面中查看 PUML 图形化效果）。核心流程（解析→提取→对比→校验）不依赖渲染环节。骨架阶段无需实现渲染，可在 UI 迭代阶段完成。

## 6. 综合结论

### 6.1 推荐技术栈（继承 Proma 版）

| 层级 | 推荐方案 | 替代方案 | 新增依赖 |
|------|----------|----------|---------|
| PUML 理解 | **LLM/Agent 原生理解**（Prompt 工程） | `plantuml-parser`（备选，需封装适配层） | **零新增**（使用已有 LLM 适配器） |
| TS 代码提取 | **TypeScript Compiler API** | ts-morph（不推荐，无必要性证据） | **零新增**（`typescript` 已存在） |
| 结构对比 | **纯自定义 ClassComparator** | 无 | **零新增**（纯 Node.js） |
| 渲染（可选） | **Proma Mermaid 组件复用** | PUML→Mermaid 转换 + `mermaid-block` | **零新增**（复用已有组件） |

### 6.2 集成复杂度：**低-中**

- **PUML 理解层**（低-中）: LLM 原生理解为主，Prompt Engineering + 格式校验；plantuml-parser 备选降级
- **代码提取层**（低）: TypeScript Compiler API 直接提取，零新依赖
- **对比逻辑层**（中）: 核心复杂度在此。纯自定义 ClassComparator，处理语义映射。建议采用可配置的规则引擎
- **渲染**（低, 可选）: PUML→Mermaid 转换字符串处理 + 复用 Proma Mermaid 组件

### 6.3 新增依赖与复用清单

| 依赖类型 | 内容 | 说明 |
|----------|------|------|
| **零新增 npm 包** | 全部四个层级 | 四层方案均完全复用 Proma 现有依赖 |
| 复用 Proma 已有能力 | `typescript` Compiler API | 代码结构提取 |
| 复用 Proma 已有能力 | `@proma/core` LLM 适配器 | LLM 原生理解 PUML |
| 复用 Proma 已有能力 | `packages/ui/src/mermaid-block/` | Mermaid 渲染 |
| 复用 Proma 已有能力 | `packages/shared/` 工具函数 | 共享类型定义和工具函数 |
| **新建 Proma 内部模块** | `PumlExtractor` 适配层 | packages/shared/ 或 packages/core/ |
| **新建 Proma 内部模块** | `ClassComparator` | packages/shared/ 或 packages/core/ |
| **新建 Proma 内部模块** | `pumlToMermaid` 转换函数 | packages/shared/ 或 packages/ui/ |

### 6.4 风险点

1. **LLM 原生理解的非确定性**
   - LLM 输出结构可能在不同调用间不一致
   - **缓解措施**: 设计 few-shot 示例 + JSON Schema 格式校验层；对 LLM 输出做后处理验证；核心字段缺失时自动重试或降级到 plantuml-parser

2. **PlantUML 语法与代码 AST 的语义鸿沟**
   - PUML 描述的是设计规约, 代码是具体实现。二者的抽象层级不同（如 PUML 可能省略 getter/setter）
   - **缓解措施**: 设计可配置的对比模式（exact / subset / contract）；允许通过注释或标记指定哪些部分需要严格校验

3. **类型文本对比的归一化问题**
   - PUML 中 `String` vs TypeScript 中 `string`；泛型参数表示方式不同
   - **缓解措施**: 建立类型映射表；在对比时对类型文本做标准化处理

4. **跨文件分析复杂度**
   - TypeScript Compiler API 的 Program 模式可以跨文件解析引用, 但完整的关系分析（关联类、聚合）需要全项目扫描
   - **缓解措施**: 初期只校验单个文件内的类结构；后续利用 Compiler API 的 `ts.createProgram()` 做全局解析

5. **PUML→Mermaid 语法转换的完整度**
   - 两种 DSL 的语法特性不完全一一对应（如 PlantUML 的 note/package/namespace）
   - **缓解措施**: 初期只转换核心类图结构（类名、属性、方法、继承、关系）；复杂特性可先跳过或降级为 LLM 生成 Mermaid 版本
