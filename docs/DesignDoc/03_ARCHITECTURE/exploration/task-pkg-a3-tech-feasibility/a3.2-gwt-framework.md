## 1. 核心理念转变

### 1.1 继承Proma原则

本平台基于 Proma fork 构建。Proma 本身就是 Agent 编程平台，测试 Agent 以 SubAgent 形式运行在 Proma 之上，天生具备以下能力：

| Proma能力 | 对应GWT测试需求 | 复用方式 |
|-----------|----------------|---------|
| **Read/Bash工具** | 读取.feature文件、执行代码、验证结果 | 直接使用，零改动 |
| **SubAgent机制** | 测试Agent作为独立角色运行 | 复用现有 `SUBAGENT_METADATA` 范式 |
| **文件系统操作** | 读写测试报告、管理测试用例 | 直接使用 `agent-workspace-manager.ts` |
| **LLM自然语言理解** | 理解Gherkin Given/When/Then语义 | Agent原生能力，无需解析器 |
| **多Session并行** | 测试Agent与编程Agent可并行工作 | 复用A2.2已验证的多Session方案 |

**关键推论**：既然LLM/Agent天生能理解自然语言，而Gherkin正是面向非技术人员设计的自然语言DSL，那么测试Agent直接读取 `.feature` 文件并逐场景验证就是最自然的方案。引入 `@cucumber/cucumber` 相当于给一个能直接读懂中文的人配了一本中文字典——多余。

### 1.2 方案调整

| 原方案 | 新方案 | 理由 |
|--------|--------|------|
| **主力**：`@cucumber/cucumber` v12.x | **主力**：Agent原生GWT执行器 | 继承Proma，非必要不引入新组件 |
| 未考虑Agent原生 | **备选**：`@cucumber/cucumber` v12.x | 当精度/性能/CI需求超过原生能力时启用 |
| `@cucumber/gherkin` 独立解析器 | **移除**（Agent可直接理解） | 不再需要独立的Gherkin解析器 |

## 2. 主力方案：Agent原生GWT执行器

### 2.1 可行性论证

**论点一：Gherkin是自然语言DSL，LLM天然可理解**

Gherkin语法本质上是一组结构化的自然语言句子：
```gherkin
Scenario: 成功添加一条读书笔记
  Given 用户在笔记列表页面
  When 用户输入书名"百年孤独"
  And 用户输入笔记内容"精彩的开篇"
  And 用户点击"保存"按钮
  Then 笔记列表中显示"百年孤独"
  And 系统提示"保存成功"
```

Given/When/Then/And/But 是英语自然词汇，步骤内容是完全自由的自然语言。LLM（尤其是深度求索、GPT、Claude等SOTA模型）无需专门的语法解析器即可理解每个步骤的语义。

**支持证据**：
- Gherkin的Feature/Scenario/Given/When/Then/And/But语法仅有7个关键字，远低于主流编程语言的语法复杂度。LLM在代码理解基准测试（如HumanEval、SWE-bench）中已证明能理解并生成Python/Java/TypeScript等完整编程语言的代码（语法复杂度远高于Gherkin）。Gherkin作为仅7个关键字的自然语言DSL，复杂度低于编程语言2-3个数量级。
- 本平台中的Agent（包括向导Agent、编程Agent）已经在日常工作中处理结构化文档：读取.md、.json、.yaml、.ts等格式文件。`.feature` 文件的解析难度低于JSON（无嵌套结构）且低于TypeScript（无类型系统），不会超出Agent现有能力边界。
- 实践中，GitHub Copilot和Cursor等基于LLM的编程辅助工具已能正确理解和自动完成 `.feature` 文件内容，验证了LLM对Gherkin格式的零样本理解能力。

**论点二：测试Agent拥有完整的验证手段**

测试Agent通过SubAgent机制运行。Proma的权限模式和工具分发机制已证明（A1.3报告第45-47行、`agent-permission-service.ts`），SubAgent的工具集可以通过 `tools` 和 `disallowedTools` 字段精确控制。具体来说，测试Agent可获得以下工具：
- **Read工具**：读取 `.feature` 文件、读取代码文件、读取测试报告（通过Proma SDK文件系统操作层，`agent-workspace-manager.ts` 管理工作区文件CRUD）
- **Bash工具**：执行 Node.js/Python 脚本、运行构建命令、检查文件系统状态（通过SDK子进程管理器，`claude-agent-adapter.ts` 中 `query()` 每次调用创建独立子进程）
- **Write工具**：写入测试结果、写入测试报告

这些工具组合起来可以覆盖GWT测试所需的全部操作：
- **Given**（前置条件）：通过 Bash 运行 setup 脚本、初始化数据库、创建测试文件
- **When**（操作）：通过 Bash 运行代码、发起 HTTP 请求、调用 API
- **Then**（验证）：通过 Bash 检查退出码/输出内容、通过 Read 检查文件状态、通过 LLM 判断结果是否符合预期

**引用链**：
- A1.3报告 §4（第45-47行）：`updateSessionPermissionMode()` 已实现运行时动态切换权限模式，工具行为随模式实时变化
- B2会话上下文报告（第49行）：`buildBuiltinAgents()` 方法注入SubAgent定义，支持 `tools`/`disallowedTools`/`prompt` 字段
- B2会话上下文报告（第440-441行）：`buildBuiltinAgents()` 位于 `agent-prompt-builder.ts:116-130`，`SUBAGENT_METADATA` 位于同文件 `:33-88`

**论点三：Proma的SubAgent机制提供了天然扩展点**

A1.3探查报告证实（第19-30行）和B2会话上下文报告（第440-441行）进一步确认，`buildBuiltinAgents()` 在 `agent-prompt-builder.ts:116-130` 定义了SubAgent的完整格式，`SUBAGENT_METADATA` 常量在 `agent-prompt-builder.ts:33-88` 维护了3个内置SubAgent定义：

```typescript
{
  description: string,        // 自然语言描述
  tools?: string[],           // 允许的工具
  disallowedTools?: string[], // 禁止的工具
  prompt?: string,            // 自定义提示词
  model?: string,             // 模型
  maxTurns?: number           // 最大轮次
}
```

测试Agent可以直接注册为新的SubAgent：
- **注册方式**：在 `SUBAGENT_METADATA`（`agent-prompt-builder.ts:33-88`）中新增一个条目
- **工具控制**：通过 `tools` 字段授予Read/Bash/Write权限，通过 `disallowedTools` 限制危险操作
- **提示词注入**：通过 `prompt` 字段注入GWT测试执行指令（见§6提示词模板）
- **零改动**：仅需添加配置项，不修改 `agent-orchestrator.ts` 或 `claude-agent-adapter.ts` 等核心编排逻辑（B2报告第166行确认MVP采用TS内联方案，与 `SUBAGENT_METADATA` 模式一致）

### 2.4 与文档体系和代码生成流程对接

```
编程Agent
  ├→ 写产品代码 → src/
  ├→ 写 .feature 文件 → features/*.feature
  │   （GWT场景已在PRD阶段由向导Agent生成）
  └→ 写测试辅助脚本（可选）→ test-utils/
      （setup.js, test-actions.js, test-query.js 等）
              │
              ▼
测试Agent（SubAgent）
  ├→ Read .feature → LLM解析场景
  ├→ Bash 执行 Each Scenario
  └→ 输出 JSON 测试报告 → reports/test-report.json
              │
              ▼
裁判Agent
  ├→ Read reports/test-report.json
  └→ 判定：全量通过？→ 交付 / 退回
```

**注意**：测试辅助脚本（test-actions.js, test-query.js）是可选项。Agent也可以直接用 Bash + curl/Node 内联命令完成操作和验证，无需预先编写辅助脚本。辅助脚本的优势在于：
- 复杂场景可复用（多个Scenario共享同样的操作步骤）
- 减少Agent的Token消耗（不必每次都生成完整命令）
- 便于调试（单独运行脚本验证）

### 2.4.1 GWT场景生命周期维护（PRD §10.3对应）

根据PRD §10.3的要求，GWT场景的生成与维护遵循以下生命周期：

| 阶段 | 操作 | 负责角色 |
|------|------|---------|
| **生成** | PRD定稿后，向导Agent为每个功能项（F-xx）自动生成对应的.feature文件 | 向导Agent |
| **补充** | 编程Agent在编码过程中发现边界条件，向.feature文件追加新Scenario | 编程Agent |
| **挑战** | 测试Agent执行时发现未覆盖的异常情况，通过裁判Agent申请补充新Scenario | 测试Agent → 裁判Agent |
| **归档** | 版本发布后，已废弃的功能对应的Scenario标记为@deprecated | 裁判Agent仲裁 |
| **删除** | 重构导致Scenario不再适用，经裁判Agent确认后删除 | 裁判Agent |

### 2.5 局限性分析

Agent原生方案并非万能，以下场景需要引入 `@cucumber/cucumber` 作为备选：

| 局限性 | 说明 | 触发阈值 |
|--------|------|---------|
| **精度敏感** | LLM对"等于""包含"等判断存在幻觉风险，需要精确断言 | 测试结果争议频繁时 |
| **大规模测试** | Agent逐场景执行在大规模（>100场景）时速度慢、Token消耗高 | 单Feature文件超过100场景 |
| **CI/CD集成** | CI/CD流水线中没有Agent环境，需要独立运行测试 | 需要部署到CI时 |
| **确定性要求** | 需要位精确、可重现的测试结果（金融/医疗等场景） | 监管合规要求 |
| **性能基准测试** | 需要精确计时、多次采样、统计分析 | 性能回归测试需求 |
| **标准化报告格式** | 需要输出JUnit/Cucumber等业界标准报告格式 | 需要对接第三方系统 |

## 3. 备选方案：@cucumber/cucumber v12.x

### 3.1 启用条件

当满足以下 **任一** 条件时，启用 `@cucumber/cucumber`：

```
如果（精度敏感 或 需要CI/CD独立运行 或 超过100场景）
  或（监管合规要求确定性测试）
  或（需要标准化报告格式对接第三方系统）
→ 启用 @cucumber/cucumber v12.x 备选方案
否则
→ 使用 Agent原生GWT执行器（主力方案）
```

### 3.2 技术选型（保留原分析）

当需要引入Cucumber类框架时，`@cucumber/cucumber` v12.x 仍是首选：

| 维度 | @cucumber/cucumber v12 | jest-cucumber v4 | quickpickle | playwright-bdd |
|------|:---:|:---:|:---:|:---:|
| 周下载量 | 250万+ | 6万+ | ~800 | 27万+ |
| 运行时 | 独立 runner | Jest 插件 | Vitest 插件 | Playwright runner |
| 编程式 API | **完整**（@cucumber/cucumber/api） | 部分（需 Jest 上下文） | 部分（需 Vitest 上下文） | 有限 |
| 动态加载 .feature | 支持 | 支持 | 支持 | 支持 |
| Step 骨架自动生成 | **内置** | 无 | 无 | 无 |
| JSON 结构化报告 | 内置 6 种 formatter | 通过 Jest reporter | 通过 Vitest reporter | 通过 Playwright reporter |
| WebContainer 兼容 | **高**（34个运行时依赖全纯JS） | 高 | 高 | 中（需浏览器二进制） |
| 零原生依赖 | **是** | 是 | 是 | 否 |

**选择理由**：架构中立、编程式API成熟、纯JS零原生依赖、与Agent执行环境完全兼容。

### 3.3 最小可行调用（备选）

```typescript
import { strict as assert } from 'assert';

Given('用户在笔记列表页面', async function () {
  // setup test state
});

When('用户输入书名{string}', async function (title: string) {
  // perform action
});

Then('笔记列表中显示{string}', async function (title: string) {
  // verify result
  assert.ok(result.includes(title));
});
```

测试Agent通过Bash启动Cucumber：
```bash
npx cucumber-js features/ --format json:reports/report.json
```

然后读取JSON报告：
```typescript
// 测试Agent通过Read工具读取报告
const report = JSON.parse(await Read("reports/report.json"));
```

## 4. 方案对比

| 维度 | Agent原生GWT执行器（主力） | @cucumber/cucumber（备选） |
|------|:---:|:---:|
| **继承Proma** | 完全复用Proma现有能力 | 引入新依赖（34个子包） |
| **新增代码量** | ~0行（仅配置SubAgent） | 安装依赖+编写step defs |
| **Token消耗** | 每场景需LLM判断，消耗较高 | 固定Token，一次运行 |
| **执行速度** | 慢（逐场景+LLM推理） | 快（原生Node.js执行） |
| **精度** | 依赖LLM判断力，存在幻觉风险 | 确定性断言，无幻觉 |
| **灵活性** | 极高（Agent可自适应调整验证方式） | 一般（需预写step defs） |
| **CI/CD集成** | 不可（需要Agent环境） | 可以（独立运行） |
| **开发者体验** | 零配置，天然与对话开发流程融合 | 需额外编写step defs代码 |
| **适合场景** | 快消型项目、小型测试集（<100场景） | 长期迭代型、大规模测试集 |
| **启动成本** | 零（Agent开箱即用） | 安装npm包+编写step defs |

## 6. Agent原生执行器的提示词模板

测试Agent的System Prompt（作为SubAgent注入）应包含以下GWT执行指令：

```markdown
## 测试执行流程

你是一个测试Agent，负责执行GWT格式的测试场景。执行流程：

1. **读取**：使用 Read 工具读取 features/*.feature 文件
2. **解析**：理解每个 Scenario 的 Given/When/Then 步骤
3. **执行**：逐场景运行，对每个步骤：
   - Given（前置条件）：使用 Bash 工具初始化测试环境
   - When（操作）：使用 Bash 工具运行测试操作
   - Then（验证）：使用 Bash/Read 工具验证结果，含精确断言
4. **报告**：输出结构化 JSON 测试报告

## 精确验证要求

- Then步骤判断必须基于**实际命令输出结果**，不能基于推理
- 使用精确断言（如 grep 精确匹配、exit code 检查）
- 对于"列表显示X"类断言，优先用 shell 命令精确匹配而非LLM判断
- 对于"系统提示Y"类断言，检查输出内容是否包含目标字符串
```

## 8. 风险

### 8.1 Agent原生方案风险

| 风险 | 级别 | 缓解 |
|------|------|------|
| LLM误判测试结果（幻觉） | 中 | 在Prompt中强调"基于实际输出验证"；备选方案兜底 |
| 执行速度慢（大规模场景） | 中 | 达到阈值时切换到备选方案 |
| 测试报告格式不一致 | 低 | 在Prompt中定义标准JSON报告模板 |

### 8.2 备选方案风险（同原报告）

| 风险 | 级别 | 缓解 |
|------|------|------|
| JSON formatter 维护模式 | 低 | 迁移至自定义 formatter（约40行） |
| Step defs 加载路径配置 | 中 | 使用绝对路径 glob |
| 并行执行在沙箱中受限 | 中 | 保持 parallel: 0 |
