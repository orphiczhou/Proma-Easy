## 1. 方案对比矩阵

### 1.1 核心方案一览

| 维度 | 方案A：全量备份 | 方案B：Git 快照 | 方案C：差异存储 | 方案D：硬链接增量快照 |
|------|:---:|:---:|:---:|:---:|
| **存储空间** | 1 分（每快照一份完整副本） | 4 分（Git 对象存储，增量） | 5 分（只存差异） | 5 分（硬链接近零成本） |
| **创建速度** | 2 分（全量拷贝，慢） | 4 分（git add 很快，commit 略慢） | 3 分（需对比 hash，遍历文件） | 4 分（hash 对比 + 硬链接，接近 git） |
| **回滚速度** | 3 分（全量复制回来） | 3 分（git checkout） | 4 分（只替换变更文件） | 5 分（目标快照目录即是完整副本） |
| **实现复杂度** | 5 分（一个 cpSync） | 2 分（需处理 Git 安装/状态/用户理解） | 2 分（需实现 diff 引擎） | 3 分（需 hash 比对 + 硬链接逻辑） |
| **可靠性** | 5 分（文件系统原生） | 3 分（Git 仓库损坏风险） | 3 分（差异链断裂风险） | 4 分（硬链接与原始文件共享 inode，误修改传播） |
| **零基础友好** | 5 分（透明） | 1 分（用户不理解 Git） | 5 分（透明） | 5 分（透明） |
| **跨平台** | 5 分（Node.js 原生） | 3 分（Windows 需安装 Git） | 5 分（纯 Node.js） | 4 分（硬链接在 Windows 可用，但跨卷有限制） |

### 1.2 评分说明

- **存储空间**：全量备份每快照 = 项目大小 N，10 个快照 = 10N；硬链接方案首快照 = N，后续约等于变更量（通常 < 5% N）。
- **创建速度**：以 50-100 个源文件的 Web 项目（排除 node_modules）为基准。
- **回滚速度**：硬链接方案的回滚是 O(1) 的复制操作，目标快照目录本身就是完整状态。
- **可靠性**：硬链接的潜在风险是误修改共享文件（通过只读快照 + 回滚时复制一份副本解决）。

## 2. 各方案详细分析

### 2.1 方案A：全量备份

优点：
- 实现极简单：一行 fs.cpSync(src, dest, { recursive: true })
- 每份快照完全独立，无连锁损坏风险
- 恢复时直接复制目录即可

缺点：
- 空间浪费巨大：10 个快照 = 10 倍项目体积
- 创建/恢复速度慢：每次需要完整遍历和拷贝
- 即使只改了一个文件也要重写全部

适用场景：项目极小（< 10MB 源码）或原型验证阶段

**实测性能参考（Node.js 22.3 fs.cpSync，Linux/macOS）**：
- 1GB 数据（含 node_modules）约 2-5 秒
- 100MB 源码约 200-500ms
- 每增加一个快照，空间线性增长

### 2.2 方案B：Git 快照

优点：
- Git 原生增量存储，空间高效
- git stash / git commit 是成熟方案
- 可方便查看历史差异

缺点：
- 目标用户不懂 Git，不能要求安装/配置
- 产品需要内嵌 Git 调用，处理各种边缘状态
- Windows 上 Git 不是预装软件
- Git 仓库损坏后恢复困难
- 用户看到 git 这个词就会产生恐惧

**相关 npm 包参考**：
- isomorphic-git：纯 JS 实现的 Git，不依赖系统 Git，但体积大（约 500KB min），性能慢 5-10 倍。

### 2.3 方案C：文件差异存储

优点：
- 只存变更文件，空间最省
- 纯 Node.js 实现，无外部依赖

缺点：
- 需维护文件变更列表 + 差异链（metadata 管理复杂）
- 回滚时需要从上一个完整基线逐层应用差异，速度随快照数量下降
- 差异链中任何一环损坏，后面所有快照不可恢复
- 实现复杂度高：需要 diff 算法或 hash 比对引擎

### 2.4 方案D：硬链接增量快照（推荐方案）

这是 rsnapshot / rsync --link-dest 模式在 Node.js 中的实现方案。

核心思想：
1. 首次快照：完整复制项目目录到 .proma/snapshots/SNAP-001/
2. 后续快照：对比文件 hash（或 mtime + size），未变更文件从上一个快照硬链接到新快照目录，变更文件完整复制到新快照目录
3. 每个快照目录都是看起来完整的项目副本
4. 回滚时：清空项目目录，将目标快照目录的全部文件复制回来

视觉化示意：

```
.proma/snapshots/
  SNAP-001/  index.js, style.css, package.json  (全量)
  SNAP-002/  index.js -> 硬链接到 SNAP-001/index.js
             style.css -> 硬链接到 SNAP-001/style.css
             package.json -> 新副本（因为变更了）
  SNAP-003/  ...
```

**为什么硬链接方案最适合本项目**：

| 特性 | 说明 |
|------|------|
| 零基础友好 | 用户完全感知不到快照存储机制，UI 只显示时间轴 |
| 空间高效 | 每快照只存储变更文件，10 个快照约 1.2-1.5 倍项目体积 |
| 回滚简单 | 目标快照就是完整目录结构，cp 或 rsync 即可恢复 |
| 独立性 | 每个快照目录可直接浏览，不依赖其他快照 |
| 删除安全 | 删除旧快照不会影响其他快照（硬链接引用计数自动管理）|
| 跨平台 | Windows NTFS 支持硬链接，fs.linkSync() 可用 |

## 3. 推荐方案

### 3.1 推荐组合：方案D（硬链接增量快照）+ 方案A（全量兜底）

**理由**：

1. **硬链接增量快照作为主方案**：空间/速度/可靠性三者最优平衡，参考 rsnapshot 和 snapback-cli 的实现思路。

2. **首快照全量 + 后续增量**：第一个快照全量复制，后续只存变更文件。当变更超过阈值（如 > 50% 文件变更）时自动触发新的全量快照作为基线。

3. **排除 node_modules**：快照只记录 package.json 和 package-lock.json，回滚后自动执行 npm ci 恢复依赖。详见第 6 节。

4. **全量兜底**：每隔 N 个快照自动创建一次全量快照作为检查点，防止增量链过长。

### 3.2 架构示意

```
项目管理器
  +-- 用户项目目录（如：/projects/my-app/）
  |     +-- src/
  |     +-- package.json
  +-- .proma/                        <- 隐藏的系统目录
        +-- snapshots/
        |     +-- SNAP-001/          <- 快照（首次全量）
        |     +-- SNAP-002/          <- 快照（增量：硬链接未变文件）
        |     +-- SNAP-003/
        +-- index.json               <- 快照元数据索引
        +-- tmp/                     <- 临时目录（用于原子回滚）
```

### 3.3 关键算法

#### 快照创建流程

```
1. 确定快照名称（SNAP-{timestamp}）
2. 检查上次快照是否存在
   2a. 首次或无上次快照 -> 全量复制：fs.cpSync(projectDir, snapDir)
   2b. 存在上次快照 -> 增量模式：
       - 遍历项目文件（排除 node_modules/.git 等）
       - 对每个文件计算 SHA256（或 mtime + size 快速比较）
       - 对比上次快照中的文件 hash
         - 未变更：fs.linkSync(prevSnapPath, newSnapPath)  （硬链接）
         - 新增/变更：fs.copyFileSync(src, dest)
       - 记录元数据（文件列表 + hash）
3. 写入 index.json 添加新快照记录
4. 标记完成
```

#### 回滚流程

```
1. 用户选择目标快照（如 SNAP-002）
2. 先自动保存当前状态为新快照（PRD 要求：回滚前保存当前版本）
3. 原子回滚：
   a. 创建临时目录 .proma/tmp/restore-{uuid}/
   b. 从目标快照复制所有文件到临时目录
      （排除 node_modules，只复制 package.json/lock 文件）
   c. 成功 -> 重命名（renameSync，文件系统级原子操作）
   d. 失败 -> 删除临时目录，保留原项目目录不变
4. 执行 npm install（如有 package.json 变化）
5. 标记回滚完成
```

| 项目类型 | 源文件数 | 源码体积（不含 node_modules） | node_modules 体积 |

### 快照空间估算（以中型 Next.js 项目为例）

| 快照数 | 方案A：全量备份 | 方案D：硬链接增量（估算） |
|--------|:--------------:|:------------------------:|
| 1 个   | 400 MB（含 node_modules） | 50 MB（排除 node_modules，仅源码） |

## 5. 性能分析

### 5.1 快照创建耗时

| 操作 | 耗时（估算） | 备注 |
|------|:-----------:|------|
| **首次全量快照**（50 MB 源码，排除 node_modules） | 0.5 - 2 s | fs.cpSync 或 fast-glob + copyFile |
| **后续增量快照**（hash 比对 + 硬链接） | 0.2 - 1 s | 遍历 100 文件 + SHA256 约 200ms |
| **回滚**（从快照恢复到项目目录） | 0.5 - 3 s | 50 MB 文件复制 |
| **npm install**（回滚后恢复 node_modules） | 20 - 60 s | 异步执行，不阻塞用户交互 |

> **用户体验要求**（来自 PRD 第 7.5 节）：超过 5 秒的操作需要显示进度提示。快照创建（< 2 秒）无需额外 UI，回滚后 npm install 需显示进度。

### 5.2 快照触发时机（PRD 定义）

| 触发时机 | 耗时预算 | 策略 |
|---------|:--------:|------|
| 初版生成时 | 2 s | 首次全量快照 |
| 用户确认修改前 | < 1 s | 增量快照（后台，无感） |
| 用户确认修改后 | < 1 s | 增量快照 |
| 模式转换时 | < 1 s | 增量快照 |
| 异常回滚前 | < 1 s | 当前状态快照（保护现场） |

### 5.3 关键优化点

- **hash 策略**：首次使用完整 SHA256，后续先用 mtime + size 快速过滤（跳过 90% 未变文件），只对有疑问的文件计算 SHA256。
- **异步不阻塞**：快照创建完全在后台 Worker Thread 执行，用户界面不卡顿。
- **延迟写入**：对大型项目的首次快照，使用流式写入而非一次性读取到内存。

## 6. node_modules 处理策略

### 结论：排除 node_modules，只记录依赖声明

**理由**：

1. **体积太大**：node_modules 占项目总空间的 80-95%，快照中的绝大部分冗余来自它。
2. **可重现性**：package-lock.json 已锁定精确版本，npm ci 保证可重现。
3. **速度**：排除 node_modules 后快照创建 < 2 秒，包含则需 10-30 秒。
4. **平台差异**：部分 npm 包包含平台特定的二进制文件（如 node-gyp rebuild 产物），跨平台回滚可能出错。

### 实现规则

| 场景 | 行为 |
|------|------|
| **创建快照时** | 忽略 node_modules/、.next/、dist/、build/、.git/ |
| **回滚时** | 从快照恢复源码后，执行 npm ci --prefer-offline |
| **优化** | 回滚前检查 package-lock.json 是否变化，未变则跳过 npm ci |

**技术细节**：
- 使用 .promaignore 文件（类似 .gitignore 语法）定义快照排除规则
- 默认排除列表：node_modules/, .next/, dist/, build/, .git/, *.log
- npm ci 通过 child_process.exec 异步运行，输出流绑定到 UI 进度指示

## 7. 回滚原子性设计

### 7.1 原子回滚协议

采用**两阶段提交**模式确保原子性：

```
阶段一（Prepare）：
  1. 在 .proma/tmp/ 下创建临时恢复目录
  2. 从快照复制所有文件到临时目录
  3. 验证文件完整性（数量 + 部分 checksum 抽样）

阶段二（Commit）：
  4. 使用 fs.renameSync() 将临时目录重命名为项目目录
     -> 文件系统级别的原子操作（重命名是原子的，NTFS/ext4/XFS 均保证）
  5. 重命名成功 -> 回滚完成
  6. 重命名失败 -> 项目目录不变，删除临时目录

  如果在阶段一崩溃 -> 临时目录残留，下次启动时自动清理
  如果在阶段二崩溃 -> 重命名要么成功要么失败，项目目录一致
  如果在阶段二和 npm install 之间崩溃 -> 源码已恢复，但 node_modules 不完整
      解决：启动时检查项目目录下是否有 node_modules，缺失则自动 npm ci
```

### 7.2 幂等性保证

- 快照是只读的：创建后永不修改，防止引用损坏
- 回滚可重复：回滚到快照 A 后再回滚到快照 A，结果一致
- 多次回滚不会产生脏状态

## 9. 边界情况处理

### 9.1 磁盘空间不足

| 场景 | 处理策略 |
|------|---------|
| 快照创建时磁盘不足 | 计算预估所需空间，不足则拒绝创建 + 提示用户清理 |
| 回滚时磁盘不足 | 创建临时目录前检查可用空间，不足则拒绝回滚 |

**技术方案**（使用 Node.js 内置 `fs.statvfs`，零依赖）：
```typescript
import { statvfsSync } from 'node:fs';

function getFreeSpace(dirPath: string): bigint {
  // fs.statvfs 返回文件系统统计信息，无需任何第三方库
  const stats = statvfsSync(dirPath);
  // f_bavail = 非 root 用户可用块数, f_bsize = 块大小
  return stats.f_bavail * stats.f_bsize;
}

function checkDiskSpace(projectDir: string, requiredSpace: bigint): void {
  const freeSpace = getFreeSpace(projectDir);
  if (freeSpace < requiredSpace * BigInt(2)) {
    throw new Error('磁盘空间不足，需要至少 ' + formatBytes(requiredSpace * BigInt(2)));
  }
}
```

> **为什么不用 check-disk-space**：`fs.statvfs` 是 Node.js 22 内置 API（`node:fs`），跨平台支持 Linux/macOS/Windows，无需引入任何第三方包。Proma 项目本身也是纯 Node.js 生态，使用内置 API 符合"继承 Proma"原则。

### 9.2 快照损坏

| 损坏类型 | 检测时机 | 处理方式 |
|---------|---------|---------|
| 文件缺失 | 回滚时校验文件清单 | 标记快照为 corrupted，尝试修复或提示用户 |
| hash 不匹配 | 回滚前抽样 checksum | 从上一个完整快照补充缺失文件 |
| metadata 损坏 | 读取 index.json 失败 | 重新扫描 snapshots 目录重建索引 |

**策略**：
- 每条快照记录附带文件清单的 hash 签名
- 回滚前验证目标快照的完整性
- 若快照损坏，自动回退到最近的上一个健康快照

### 9.3 并发快照

| 场景 | 风险 | 处理方式 |
|------|------|---------|
| 用户快速连续操作触发多个快照 | 竞态条件，新快照覆盖旧快照 | 复用 Proma `safe-file.ts` 的原子写入模式：快照引擎通过 `activeSessions` Map 持有互斥锁，同一时间只允许一个快照操作 |
| 快照创建中用户关闭应用 | 快照不完整 | 创建临时标记文件，启动时检测 + 清理未完成快照 |

**Concurrency Control**（复用 Proma 的 `activeSessions` Map 模式）：

Proma 的 `safe-file.ts` 实现了崩溃安全的原子写入（备份→临时文件→rename），其核心模式可自然扩展到快照操作的并发控制。

```typescript
// 参考 Proma safe-file.ts 的原子写入模式 + activeSessions Map 互斥
import { randomUUID } from 'node:crypto';

class SnapshotLock {
```

> **为什么不引入 proper-lockfile**：Proma 的 `safe-file.ts` 已实现崩溃安全的原子写入，`activeSessions` Map 提供了进程内互斥的基础模式。快照场景是单用户桌面端（非多进程竞争），无需 OS 级文件锁。Stack 化 Promise 足够保证操作的串行执行。需要扩展为 IPC 级别锁时，可在 `activeSessions` Map 基础上增加文件心跳标记。

### 9.4 硬链接的特殊边界

| 边界 | 风险 | 处理 |
|------|------|------|
| 跨卷硬链接 | fs.linkSync() 会抛出 EXDEV 错误 | 检测到跨卷时回退到文件复制 |
| FAT32/exFAT 不支持硬链接 | 同上 | 检测文件系统类型，不支持时回退到复制 |
| 硬链接数超过限制 | NTFS 硬链接上限 1024 个 | 超过 900 时自动触发全量快照重置 |
| 用户误修改快照目录文件 | 污染所有共享同一 inode 的快照 | 快照目录权限设为只读（OS 级 chmod 或 ACL）|

## 12. 总结

**核心结论**：硬链接增量快照（方案D）是本项目最合适的选择。

- 空间效率接近差异存储，但实现简单可靠得多
- 每个快照是完整的目录树，回退无差异链断裂风险
- 纯 Node.js 实现，零外部依赖（Git/rsync），Windows/Linux/macOS 全兼容
- 10 个快照仅占用约 50-100 MB（全部源码）
- 快照创建 < 2 秒，回滚 < 3 秒（不含 npm install）
- 通过两阶段提交 + 文件重命名实现原子回滚
- node_modules 排除后按需恢复，避免 80-95% 的冗余存储
