# A2.1 多 System Prompt 动态切换可行性分析

## 目标验证

同一用户会话中，根据项目阶段动态切换 4 个角色（需求分析师 / UIUX 顾问 / 架构设计师 / 工程经理），每个角色有独立的 System Prompt 和模型。

---

## 调查项 1：sendMessage() 中 Prompt 的构建时机

### 当前实现方式

agent-orchestrator.ts 中 sendMessage() 方法（第 932 行）在**每次用户发消息时**重新构建完整的 queryOptions，包括 System Prompt。

具体流程（第 1228-1540 行）：

```
每次 sendMessage() 调用:
  +-- buildSystemPrompt({...})    <= 每次都重新构建
  +-- queryOptions.systemPrompt = { type: preset, preset: claude_code, append: prompt }
  +-- this.adapter.query(queryOptions)   <= 传入 SDK
```

关键代码（第 1527-1539 行）：

```typescript
systemPrompt: {
  type: preset,
  preset: claude_code,
  append: buildSystemPrompt({
    workspaceName, workspaceSlug, sessionId,
    permissionMode, memoryEnabled,
    claudeAvailable, deepSeekSubagentModel,
  }),
}
```

但是：第二次及后续消息走 **SDK resume 机制**（第 1273-1275 行）：

```typescript
const finalPrompt = existingSdkSessionId
  ? contextualMessage          // resume 模式：只传用户消息
  : buildContextPrompt(...)    // 新会话：回填历史
```

resume 会让 SDK 保持原始会话状态，包括第一次创建的 System Prompt。**后续消息即使重新构建了 append 内容，SDK 也不会重新应用它**（SDK 内部在 session 生命周期内只读取一次 systemPrompt）。

### 可行性结论

| 场景 | System Prompt 是否生效 |
|------|----------------------|
| 首次消息（新 SDK session） | 完全生效 |
| 后续消息（resume 模式） | SDK 忽略新的 append，沿用首次的 |
| 切换角色后重新开始 | 需要清除 sdkSessionId，创建新 SDK session |

**结论：当前实现本质上是"一次设定，终身使用"。** 每次 sendMessage() 虽然在 JS 层重建了 prompt 对象，但 SDK 的 resume 机制使后续消息不会重新加载 systemPrompt。要实现动态切换，必须干预 SDK session 生命周期。

## 调查项 2：buildSystemPrompt() 的输入参数 SystemPromptContext

### 当前实现方式

agent-prompt-builder.ts 第 133-143 行定义的接口：

```typescript
interface SystemPromptContext {
  workspaceName?: string
  workspaceSlug?: string
  sessionId: string
  permissionMode: PromaPermissionMode
  memoryEnabled: boolean
  claudeAvailable?: boolean
  deepSeekSubagentModel?: string
}
```

buildSystemPrompt() 的输出结构（第 155-474 行）：

1. Agent 角色定义（硬编码为 Proma Agent）
2. 工具使用指南
3. SubAgent 委派策略（按渠道分 3 个分支）
4. 用户信息
5. 工作区信息
6. 不确定性处理
7. 计划模式指令
8. 记忆系统指引
9. 文档输出与知识管理
10. 任务完成标准
11. 交互规范

### 扩展可行性

可以在 SystemPromptContext 中添加一个 rolePrompt?: string 字段，然后在 buildSystemPrompt() 的 sections 数组开头注入角色自定义指令。

这样角色 Prompt 会被放在最前面，优先级最高。但 **这只是解决了 prompt 的构建问题，没有解决运行时切换问题**——System Prompt 仍只在 SDK session 创建时生效。

### 可行性结论

**可以扩展。** 改动很小，只需：
- 向 SystemPromptContext 加一个字段
- 在 buildSystemPrompt() 的 sections 中注入
- 从上层传入当前角色的 prompt 文本

但这只是必要条件，不是充分条件。

## 调查项 3：SubAgent 机制能否用于角色切换

### 当前实现方式

SubAgent 是 SDK 的 agents 选项，在 Proma 中注册了 3 个预定义 SubAgent（agent-prompt-builder.ts 第 33-88 行）：

| SubAgent | 用途 | 默认模型 |
|----------|------|---------|
| code-reviewer | 代码审查 | haiku |
| explorer | 代码库探索 | haiku |
| researcher | 技术调研 | haiku |

SubAgent 通过主 Agent 的 Agent 工具调用，本质是主 Agent 委派子任务，完成后结果回到主上下文。

### 角色切换方案的局限性

1. **主 Agent 仍存在**：用户始终和 Proma Agent 对话，SubAgent 只是临时被调用
2. **SubAgent 是短暂的任务**：每次调用创建新子进程，完成后销毁，不存在持续扮演一个角色
3. **上下文隔离**：SubAgent 看不到主会话完整历史
4. **不能指定模型**：非 Claude 渠道继承主模型，Claude 渠道默认 haiku

### 可行性结论

**不适合作为角色切换的主要机制。** SubAgent 适用于主 Agent 委派子任务的场景，不适合用户切换自己扮演的角色。

## 调查项 4：SDK query() 的中断与新 Query 启动（软重启）

### 当前实现方式

claude-agent-adapter.ts 提供 3 个操作：

| 方法 | 作用 | 对 SDK session 的影响 |
|------|------|---------------------|
| abort(sessionId) | 杀子进程 + 清理 | 完全终止 |
| interruptQuery(sessionId) | 软中断当前 turn | 保留子进程和消息通道 |
| sendQueuedMessage(sessionId, msg) | 注入队列消息 | 通过通道继续驱动 |

Orchestrator 中已有中断 + 续跑的完整实现（queueMessage() 第 2294 行）。

### 软重启的方案

可以实现一个软重启流程来切换 System Prompt：

1. stop(sessionId) -- 终止当前 SDK session（杀进程 + 清 activeSessions）
2. updateAgentSessionMeta({sdkSessionId: undefined}) -- 清除 resume 关系
3. 用户切换角色
4. sendMessage({...}) -- 重新创建新 SDK session
   - existingSdkSessionId = undefined 触发 buildContextPrompt() 回填历史
   - buildSystemPrompt() 包含新角色 Prompt
   - this.adapter.query(queryOptions) 创建新 SDK session

### 更好的方式：buildRecoveryPrompt()

代码库中已有更完整的上下文恢复方案（第 370-390 行）：

buildRecoveryPrompt() 注入 <session_recovery> 标签，指向完整的 JSONL 历史文件，Agent 自动读取恢复上下文。

这个方法在 prepareResumeFallbackRecovery()（第 861 行）中已被使用——当 resume 失败时自动切换到 recovery 模式。**不需要额外开发**。

### 可行性结论

**软重启完全可行。** 现有基础设施已支持：
- stop() 终止旧 SDK session
- buildContextPrompt() 回填最近 20 条消息
- buildRecoveryPrompt() 完整 JSONL 自引用（已有生产代码）
- prepareResumeFallbackRecovery() 切换逻辑模板

## 调查项 5：SDK Resume 机制能否跨 Prompt 保持上下文

### 当前实现方式

SDK 根据 resumeSessionId 找到本地持久化的 session，恢复全部上下文，包括原始 System Prompt。

Orchestrator 对 resume 的判断（第 1273-1275 行）：
- existingSdkSessionId 存在：只传用户消息，SDK 自动衔接
- existingSdkSessionId 不存在：调用 buildContextPrompt() 回填历史

### 跨 Prompt 上下文保持的方案

不能直接用 SDK resume 来跨 Prompt 保持上下文，因为 resume 会恢复旧的 System Prompt。正确做法：

1. 清除 sdkSessionId（不 resume）
2. 用 buildRecoveryPrompt() 注入 session 自引用，让 Agent 读取完整 JSONL 历史
3. 新的 System Prompt 包含角色定义

代码库中已有完整实现路径：
prepareResumeFallbackRecovery()
  -> updateAgentSessionMeta(sdkSessionId: undefined)
  -> queryOptions.prompt = buildRecoveryPrompt(...)
  -> queryOptions.resumeSessionId = undefined

### 可行性结论

**可以跨 Prompt 保持上下文，但不能用 SDK resume。** 需要使用 Proma 自己的 buildRecoveryPrompt() 机制：
- Agent 通过 <session_recovery> 标签读取 JSONL 历史
- 新 SDK session 携带新的 System Prompt
- 上下文通过 JSONL 自引用来恢复

## 综合结论

### 推荐方案：Hybrid - Session Restart + Context Backfill

将以下已有机制组合：

```
用户切换角色
  |
  +-- 1. 更新 AgentSessionMeta.rolePromptId（持久化角色选择）
  +-- 2. clearSdkSession(sessionId)
  |     +-- activeSessions.delete(sessionId)
  |     +-- updateAgentSessionMeta(sdkSessionId: undefined)
  |
  +-- 3. 下一次 sendMessage() 自动触发：
        +-- existingSdkSessionId = undefined
        +-- buildSystemPrompt({rolePrompt: content})
        +-- buildRecoveryPrompt(...)
        +-- this.adapter.query(queryOptions)
```

### 实现注意事项

1. **切换时机**：必须在 Agent 空闲时（activeSessions 不含该 session）切换。
2. **上下文恢复延迟**：切换后首次响应可能需要额外一次工具调用（Read JSONL 文件），这是 buildRecoveryPrompt() 的设计预期。
3. **系统提示词分离**：角色提示词和 Proma 框架指令应当保持独立 sections。
4. **前端体验**：切换时展示过渡状态，用 eventBus 发射事件通知 UI。
5. **错误降级**：如果切换失败，回退到之前角色继续。
