## 功能回顾

用户在使用预览原型时，点击不满意的界面元素 → 系统高亮该元素 → 向导Agent询问修改意图 → 用户自然语言描述 → 编程Agent修改代码 → 预览刷新。

我们的 wireframes 中，每个可交互元素已标注 `data-ai-id` 属性。

## 候选方案对比

### 方案A：data-ai-id 标注

- **原理**：原型生成时给每个可交互元素注入唯一 `data-ai-id`（如 `data-ai-id="btn-submit"`），前端捕获点击 → 读取 `data-ai-id` → 传给Agent
- **优点**：精确、稳定、不受DOM结构变化影响
- **缺点**：需要原型生成Agent和编程Agent约定ID命名规范；用户项目的原型也需要注入

### 方案B：DOM路径（XPath/CSS Selector）

- **原理**：点击时记录元素在DOM树中的路径，传给Agent定位
- **优点**：不需要预先标注，通用性强
- **缺点**：DOM结构变化后路径失效；路径冗长不利于Agent理解

### 方案C：截图+视觉模型定位

- **原理**：截图预览页面 → 视觉模型识别用户点击位置对应的UI元素 → 生成修改规约
- **优点**：最接近人类直觉，不依赖标注
- **缺点**：视觉模型准确率不稳定；截图→识别→修改链路长

### 方案D：混合方案

- **原理**：data-ai-id 为主路径（自己的原型），截图+视觉为兜底（用户截图标注的场景）

## 输出要求

产出一份 `click-to-fix-report.md` 放在本文件夹内，包含：

1. **方案对比矩阵**：填完上表，给出每格评分和理由
2. **推荐方案**：Phase 1 用什么？后续如何演进？
3. **完整交互链路**：从用户点击到代码修改的端到端流程（每一步做什么、谁来做）
4. **data-ai-id 命名规范草案**（如果选A/D）：按钮/输入框/卡片/导航等元素的命名约定

6. **风险点**：误识别、元素不存在、连续快速点击等边界情况如何处理
