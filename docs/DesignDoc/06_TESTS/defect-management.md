## §1 严重等级定义

### §1.1 三级划分总览

| 等级 | 名称 | 一句话定义 | 默认响应 SLA | 默认修复 SLA | 是否阻塞 Sprint 验收 |
|------|------|-----------|-------------|-------------|-------------------|
| **P0** | 阻断（Blocker） | 主流程不可用 / 数据永久损失 / 安全边界突破 / 不可绕过 | ≤ 4 小时 | ≤ 1 工作日（当前 Sprint 内强制清零） | ✅ 是（必须清零才能验收） |
| **P1** | 严重（Critical） | 重要功能受损但有 workaround / 偶发主流程失败 / 临时可恢复数据问题 | ≤ 1 工作日 | ≤ 当前 Sprint 内，或最迟下一 Sprint | ⚠️ 有条件（见 §4.1） |
| **P2** | 建议（Minor） | 体验问题 / 边角案例 / 性能与可读性优化 / 非功能性建议 | ≤ 1 Sprint | 按 backlog 优先级排期 | ❌ 否（进 backlog） |

### §1.2 客观判定标准（五维度决策矩阵）

> **判定原则**：等级由**客观维度评分**决定，而非主观感受。测试工程师按下表五维度逐项打分，取**最高触及等级**为最终等级（就高不就低）。任一维度触达 P0 即整体 P0。

| 维度 | P0 触发条件 | P1 触发条件 | P2 触发条件 |
|------|------------|------------|------------|
| **D1 影响范围** | 全用户 / 多模块 / 主流程（mode-select → delivered 链路任一节点） | 部分用户 / 单模块 / 非主流程功能 | 单一边角场景 / 特定平台特定输入 |
| **D2 可绕过性** | 不可绕过（无替代路径，用户无法继续） | 有 workaround 但体验显著下降 | 有简便绕过 / 仅偶发可重试成功 |
| **D3 数据损失** | 永久数据丢失 / `_meta.json`/JSONL/snapshot 损坏不可恢复 | 临时数据问题（可重试/可重建） | 无数据影响 |
| **D4 安全边界** | 沙箱逃逸（[[03_ARCHITECTURE/architecture.md]] §6 L0/L1 失效）/ 权限突破（B5 manual 伪造成功 [[04_API_SPEC/api-spec.md]] §0.4）/ PII 原文泄露（脱敏失效） | 拒绝行为副作用非零（业务逻辑部分执行，对齐 test-plan §11.7）但未达逃逸 | 无安全影响 |
| **D5 用户感知 / 时序不变量** | 主流程阻断 / 时序不变量 ORD-01~07 违反（[[04_API_SPEC/events.md]] §4.3）/ 熔断回滚链路断裂（test-plan §11.6） | 偶发主流程失败 / 软约束评估异常降级 / 单埋点字段错 | 文案/样式/性能微瑕 |

### §1.3 等级判定决策树

```text
缺陷发生 → 依次回答：
  Q1: D4 安全边界是否触达 P0？（沙箱逃逸/权限突破/PII 泄露）
      是 → P0（终止）
      否 → Q2
  Q2: D3 是否永久数据损失 / 文件损坏不可恢复？
      是 → P0（终止）
      否 → Q3
  Q3: D1+D2 是否主流程不可绕过阻断？（mode-select→delivered 任一节点不可继续）
      是 → P0（终止）
      否 → Q4
  Q4: D5 是否时序不变量违反 / 熔断回滚链路断裂？
      是 → P0（终止）
      否 → Q5
  Q5: D1 是否部分用户/单模块重要功能受损？或 D2 有显著 workaround？或 D3 临时可恢复？
      是 → P1
      否 → P2（体验/边角/优化）
```

### §1.4 边界案例与升级/降级规则

| 情形 | 规则 |
|------|------|
| 测试环境 mock 失败 vs 真实环境 | 以真实 fs / IPC harness 环境为准（test-plan §7.2）；mock-only 失败降一级 |
| 间歇性复现（flaky） | 复现率 ≥ 30% 按 P1；< 30% 但主流程按 P2 追踪并标注 `flaky`；连续 3 次 nightly 触发自动升 P1 |
| 拒绝行为副作用非零（test-plan §11.7） | 默认 P1；若副作用涉及安全/数据则升 P0（按 D4/D3 复核） |
| 同一 TC-ID 重复缺陷（重开 ≥ 2 次） | 自动升一级（P2→P1，P1→P0），触发根因分析 |
| 修复后回归出新缺陷 | 新 issue 独立定级，原 issue 不重开（避免 SLA 混乱） |
| 等级争议 | 代码审查员仲裁；跨模块争议由工程经理角色（sprint-plan §4.1）裁决 |

## §2 Issue 模板

### §2.1 模板字段（10 字段标准结构）

| # | 字段 | 必填 | 说明 |
|---|------|------|------|
| 1 | **标题** | ✅ | 命名规范见 §2.2，含等级标签 + 模块 + 简述 |
| 2 | **描述** | ✅ | 缺陷现象一句话概述 + 影响哪个用户故事/功能 |
| 3 | **复现步骤** | ✅ | 编号步骤，可独立重现（含输入数据/环境/前置条件） |
| 4 | **期望结果** | ✅ | 对齐 test-plan 用例"期望输出"列 + §11 判据 PASS 信号 |
| 5 | **实际结果** | ✅ | 含错误码 / 异常栈 / 实际 events 序列 / 文件状态截图 |
| 6 | **严重等级** | ✅ | P0/P1/P2 + 五维度（D1~D5）触达依据 |
| 7 | **归属 Sprint** | ✅ | S1~S13（对齐 sprint-plan §2.2 矩阵） |
| 8 | **归属用例 TC-ID** | ✅ | test-plan 三段式 ID（如 TC-BOUND-198），多对多可列多个 |
| 9 | **状态** | ✅ | 新建 / 已分配 / 修复中 / 待验证 / 已关闭 / 重开（见 §3.1） |
| 10 | **指派人** | ✅ | 全栈开发（修复）/ 测试工程师（验证）/ 代码审查员（审查） |

> **可选补充字段**：环境（OS/Electron 版本）/ 日志路径 / 关联 PR / 根因分析（P0/P1 必填）/ 修复用例 TC-ID（新增的回归用例）。

### §2.2 标题命名规范

格式：`[<等级>][<模块>] <简述>`

| 元素 | 取值 | 示例 |
|------|------|------|
| 等级 | P0 / P1 / P2 | `[P0]` |
| 模块 | CODER/GUIDE/JUDGE/SNAPSHOT/TELEMETRY/PROJECT/EVENT/EXCEPT/SPRINT/BOUND/INFRA + 业务模块名 | `[BOUND-沙箱]` |
| 简述 | 动宾结构，含失败场景 | `L0 路径越界未触发 CODER_FIX_OUT_OF_SCOPE` |

**完整示例**：`[P0][BOUND-沙箱] L0 路径越界未触发 CODER_FIX_OUT_OF_SCOPE，_code/ 外文件被改`

### §2.3 完整模板示例

```markdown
**标题**: [P0][BOUND-沙箱] L0 路径越界未触发 CODER_FIX_OUT_OF_SCOPE，_code/ 外文件被改

**描述**: coder.applyFix 在修改触及 `_code/` 外文件时，未按 test-plan TC-BOUND-206 返回 CODER_FIX_OUT_OF_SCOPE，导致沙箱 L0 边界失效，AI 生成代码可改项目根任意文件。影响安全边界 D4。

**复现步骤**:
1. 启动应用，创建 quick 项目，完成原型确认进入 coding 阶段
2. mock 一个 fixSpec，其 target 路径指向 `{projectRoot}/_meta.json`（`_code/` 外）
3. 调用 coder.applyFix 执行该 fixSpec
4. 检查 `_meta.json` 文件 hash

**期望结果**: error.code='CODER_FIX_OUT_OF_SCOPE'（403 不可重试）；`_code/` 外文件 hash 不变（test-plan §11.7 沙箱 L0 路径 PASS 信号）。

**实际结果**: success=true；`_meta.json` 被修改，hash 变化；未返回任何错误码。

**严重等级**: P0
- D1 影响范围: 全用户（沙箱是所有 coding 阶段必经）— 触达 P0
- D2 可绕过性: 不可绕过 — 触达 P0
- D3 数据损失: `_meta.json` 损坏可致项目元数据失真 — 触达 P0
- D4 安全边界: L0 边界失效，AI 可改任意文件 — 触达 P0
- D5 用户感知: 主流程安全链路断裂 — 触达 P0

**归属 Sprint**: S3（沙箱 L0 首次落地，sprint-plan §3.3）

**归属用例 TC-ID**: TC-BOUND-206（对齐 test-plan §6.4）

**状态**: 新建

**指派人**: @全栈开发（修复）/ 待测试工程师（验证）
```

## §3 分配 / 修复 / 验证 / 关闭闭环准则

### §3.1 状态机（发现 → 分配 → 修复 → 验证 → 关闭）

```text
[新建 New] --(测试工程师提交)--> [已分配 Assigned]
[已分配]   --(指派给全栈开发)--> [修复中 In-Progress]
[修复中]   --(提交修复 PR + 回归用例)--> [待验证 Pending-Verify]
[待验证]   --(测试工程师回归测试通过)--> [已关闭 Closed]
[待验证]   --(回归测试未通过)--> [重开 Reopened] --> [修复中]
[已关闭]   --(后续版本复现)--> [重开 Reopened]（重新定级，触发升级规则 §1.4）
```

| 状态 | 责任人 | 进入条件 | 退出条件 |
|------|--------|---------|---------|
| 新建 | 测试工程师 | 用例 FAIL，提交 issue（10 字段齐全） | 被指派/确认有效 |
| 已分配 | 工程经理角色 / 代码审查员 | issue 确认有效并定级 | 全栈开发接手 |
| 修复中 | 全栈开发 | 接手 issue | 提交修复 PR + 新增/更新回归用例 |
| 待验证 | 测试工程师 | PR 提交 + 代码审查通过 | 回归测试执行 |
| 已关闭 | 测试工程师 | 回归测试通过（验证证据见 §3.3） | — |
| 重开 | 测试工程师 | 回归未通过 / 后续版本复现 | 重新修复 |

> **单向闭环原则**：不允许"已关闭"直接跳回"新建"；重开必须保留原 issue 历史，便于根因追溯与 §1.4 升级规则触发。

### §3.2 各级 SLA（响应 + 修复 + 验证）

| 等级 | 响应 SLA（已分配） | 修复 SLA（待验证） | 验证 SLA（已关闭） | 超时升级 |
|------|------------------|------------------|------------------|---------|
| **P0** | ≤ 4 小时 | ≤ 1 工作日 | ≤ 4 小时（优先回归） | 修复超时 → 每日站会通报 + 工程经理介入 |
| **P1** | ≤ 1 工作日 | ≤ 当前 Sprint 内；最迟下一 Sprint | ≤ 1 工作日 | 跨 Sprint → 自动升 P0 阻塞下 Sprint 验收 |
| **P2** | ≤ 1 Sprint | 按 backlog 优先级 | ≤ 1 Sprint | 不阻塞，定期复盘 |

> **SLA 计时起点**：从"已分配"状态进入时刻起算（而非"新建"），避免争议期占用修复时间。
> **非工作时间**：夜间/周末不计入 SLA（与 team-config 工作日口径一致）。

### §3.3 验证证据要求（按等级差异化）

| 等级 | 验证证据最低要求 | 验证人 |
|------|----------------|--------|
| **P0** | ① 失败用例对应的 `.test.ts` 回归用例通过（含新增用例） ② E2E 复现链路全绿（若涉及用户感知） ③ **双人验证**：修复者 + 另一人（测试工程师或代码审查员）独立确认 ④ 根因分析记录（写入 issue 评论） | 测试工程师 + 代码审查员 |
| **P1** | ① 失败用例回归通过 ② 修复者自测 + 测试工程师回归 ③ 根因分析（简版，写入评论） | 测试工程师 |
| **P2** | ① 修复者自测通过 ② 测试工程师抽样回归 | 测试工程师 |

> **回归用例强制要求**（全等级）：每个缺陷**必须**新增或更新至少一条回归用例绑定到原 TC-ID（或新建 TC-ID 并在 issue 中声明），防止同类缺陷复发。这是"已关闭"的前置条件——没有回归用例的修复不得关闭。
>
> **验证证据留痕**：回归用例执行日志 / Playwright 截图 / telemetry.query 反查结果（事件类缺陷）须作为附件或评论链接留存，便于后续审计与 macp 式回顾。

| 角色 | 发现 | 定级 | 分配 | 修复 | 审查 | 验证 | 关闭 |
|------|------|------|------|------|------|------|------|
| 测试工程师 | ✅ 主导 | ✅ 提议（按 §1 矩阵） | — | — | — | ✅ 主导 | ✅ |

| 代码审查员 | 辅助 | ✅ 仲裁 | ✅ 主导 | — | ✅ 主导 | 辅助（P0 双人） | — |
| 工程经理角色 | — | ✅ 跨模块裁决 | ✅ 统筹 | — | — | — | — |

## §4 Sprint 联动机制

### §4.1 P0 缺陷阻塞 Sprint 验收

**硬规则**：Sprint 验收 DoD（Definition of Done）必须满足"P0 缺陷清零"。

| 等级 | 对 Sprint 验收的影响 |
|------|-------------------|
| **P0** | 🔴 **硬阻塞**：当前 Sprint 存在未关闭 P0 → Sprint 不可验收，不可进入下一 Sprint 的依赖项（如 S2 依赖 S1，S1 有 P0 则 S2 启动受阻）。例外：经工程经理 + 测试工程师联合签字的"已知 P0 + 缓解方案 + 下 Sprint 强制清零"可临时放行，但须在 Sprint 验收记录备案。 |
| **P1** | ⚠️ **有条件携带**：允许带 P1 进入下一 Sprint，但须计入下一 Sprint 容量（sprint-plan §3.4 工时汇总），且不得是"主流程不可绕过"类（否则应升 P0）。携带 P1 数量上限 = 团队规模（2-3 人团队 → 最多 2-3 个 P1 跨 Sprint）。 |
| **P2** | 🟢 **进 backlog**：不影响验收，按优先级排期。 |

**验收前自检清单**（Sprint 验收时测试工程师执行）：
- [ ] 本 Sprint 新增 P0 全部已关闭（回归用例 + 双人验证）
- [ ] 跨 Sprint 携带的 P1 总数未超上限
- [ ] 重开 ≥ 2 次的缺陷已完成根因分析
- [ ] test-plan §5（S1-S3）/ §10（S4-S13）对应 Sprint 的 TC-SPRINT-* 验收用例全绿

### §4.2 缺陷在 Sprint 间流转

```text
Sprint N 验收 → P0 残留?
  是 → 阻塞，不可进入 Sprint N+1（或联合签字临时放行 + 备案）
  否 → P1 携带检查:
        携带数 ≤ 上限 → P1 转入 Sprint N+1 容量
        携带数 > 上限 → 升级处理（P1→P0 风险评估）
P2 → 全部转入 backlog，按优先级排序
```

| 流转情形 | 规则 |
|---------|------|
| P0 跨 Sprint | 默认禁止；联合签字放行的 P0 须在下一 Sprint Day-1 优先修复 |
| P1 跨 Sprint | 计入下一 Sprint 容量（工时按 sprint-plan §3.4 估算口径） |
| P2 跨 Sprint | 自由流转，无容量约束 |
| 缺陷归属 Sprint 修正 | 若发现定级时归属错误（如 S3 缺陷误归 S5），须在 issue 评论记录修正理由 + 重指派 |

### §4.3 Release 前清零准则

**Release（版本发布）DoD**：

| 等级 | Release 前要求 |
|------|--------------|
| **P0** | 🔴 **必须清零**：零未关闭 P0；已关闭 P0 全部有回归用例 + 双人验证证据 |
| **P1** | 🔴 **必须清零或进入"已知缺陷清单"**：未关闭 P1 须逐条评估，经发布负责人签字列入 Release Notes 的"已知问题"，且每条有 workaround 说明 |
| **P2** | 🟢 **可携带**：不阻塞发布，列入 backlog |

**Release 前测试矩阵**（对齐 test-plan §7.3）：
- ✅ 全量单元测试通过（coverage ≥ 80%/70%）
- ✅ 全量集成测试通过（nightly 绿）

- ✅ 时序不变量 ORD-01~07 全量场景满足（test-plan §11.5）
- ✅ P0 清零、P1 清零或备案、P2 入 backlog
- ✅ 所有关闭缺陷的回归用例执行日志留存

### §4.4 缺陷燃尽图与 DoD 量化

每个 Sprint 维护**缺陷燃尽图**（P0/P1 分列），跟踪：
- 新增缺陷数（按 TC-DOMAIN 分布）
- 关闭缺陷数（按 SLA 达成率）
- 携带缺陷数（跨 Sprint 流转）
- 平均修复时长（MTTR，按等级）

**DoD 量化指标**（Sprint 验收门槛）：
- P0 关闭率 = 100%（强制）
- P1 关闭率 ≥ 80%（剩余备案携带）
- P0 平均修复时长 ≤ 1 工作日（SLA 达成）
- 回归用例新增率 = 100%（每关闭缺陷必有用例）

## §5 与 test-plan / sprint-plan 对齐

### §5.1 用例 TC-ID 反向追溯

每个缺陷的"归属用例 TC-ID"字段建立**缺陷 ↔ 用例**双向链接：

| 缺陷来源 | TC-ID 范围 | 对应 test-plan 章节 |
|---------|----------|-------------------|
| 端点契约失败 | TC-CODER/GUIDE/JUDGE/SNAPSHOT/TELEMETRY/PROJECT-001~112 | §2 |
| events 触发失败 | TC-EVENT-113~133 | §3 |
| 异常自愈失败 | TC-EXCEPT-134~154 | §4 |
| Sprint S1-S3 验收失败 | TC-SPRINT-155~183 | §5 |
| 权限边界失败 | TC-BOUND-184~209 | §6 |
| Phase 2-4 验收失败 | TC-SPRINT-210~309 | §10 |

> **追溯价值**：缺陷可反向追溯到具体 TC-ID → test-plan 章节 → 上游基准文档（api-spec/events/sprint-plan），形成"缺陷-用例-设计"三向闭环，便于根因定位与回归范围评估。

### §5.2 严重等级与 test-plan §11 判据的映射

| 严重等级 | test-plan §11 对应"FAIL 当"信号 | 映射关系 |
|---------|------------------------------|---------|
| **P0** | §11.6 熔断触发信号 FAIL（未熔断继续重试）/ §11.7 业务逻辑未执行 FAIL（拒绝后仍有副作用，涉安全）/ §11.5 时序不变量违反 / §11.2 原子写不变量 FAIL（_meta.json 损坏） | FAIL 信号触达安全/数据/主流程 → P0 |
| **P1** | §11.4 错误码精确匹配 FAIL（返回通用码而预期专属）/ §11.5 payload 字段匹配 FAIL（缺字段）/ §11.6 通俗化通知文案 FAIL（含黑名单词） | FAIL 信号触达功能正确性但可 workaround → P1 |
| **P2** | §11.3 跨平台一致性 FAIL（某平台截图差异）/ §11.1 覆盖率门槛边际未达 | FAIL 信号仅体验/边角 → P2 |
