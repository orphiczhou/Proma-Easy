## 交互1：点选纠错（Click-to-Fix）

> v0.4 说明：本节以产品实现（linux-support 分支 v0.17.47–v0.17.55）为单一事实源重写。旧版 v0.3 的原型描述见文末“与v0.3 spec的差异说明”。

### 触发条件
- 前置：用户正在预览区查看HTML原型，原型中可交互元素已标记 `data-ai-id` / `data-ai-type`（快消型工作区使用`data-ai-id` + `data-ai-type`；长期迭代型工作区使用`data-el`自定义属性）
- 触发：用户点击预览区中的界面元素
- 并列展示（v0.17.55）：点选交互各时机（首次改动入清单、改文字/其他输入、语音意见、接受本轮改动）自动把预览独立 tab 转为会话内右侧分屏（聊天与原型并排），保证用户始终边看原型边交互
- PRD追溯：§7.3 | US-U05（6个GWT场景）

### 核心原则（v0.17.48 起）
- **即时调整不逐次打扰 Agent**：换颜色/删掉/换位置直接在原型上即时生效（可连续多处），修改先累积后统一接受
- **意见收集轮硬门禁**（v0.17.51）：意见收集阶段收到单条意见只允许记录+确认+追问，用户明确说收齐后才批量执行（防逐条改文件）

### 步骤序列（实现流程）

```
[触发] 用户点击原型元素
  → [系统] 事件委托捕获 click → 读取 data-ai-id(或 data-el)/type/rect（去重 + 会话级上限24条）
  → [视觉] 高亮应用到被点击元素（3秒自动消失，选择后提前消失）
  → [视觉] 快速选项面板弹在元素下方（空间不足自动上移）
  → [用户选择]：
     A. 换颜色 → 4预设色 + 🎨自定义调色板，点击即生效
     B. 删掉它 → 元素即时半透明（模拟删除），可撤销
     C. 换个位置 → 拖拽模式：iframe 内直接拖动元素，松手偏移入清单
        （位移<4px 视为误触不上报；拖后400ms 抑制 click 误重选；高分屏阈值按 devicePixelRatio 归一）
     D. 改文字 / 其他 → 切回会话 tab + 聚焦输入框，元素引用随消息携带（<ux-element-ref>）
     E. 🎤语音 → 复用内置语音听写，识别结果自动附在当前选中元素上
     F. 点击面板外 / 取消 → 关闭
  → [即时效果] iframe 内 inline 应用，原始样式可撤销；元素右上角红色计数角标 +
     元素下方窄条（靛蓝底白字）显示改动摘要，点击角标/窄条看全部意见（编号列表）
  → [累积] 待接受清单：预览窗口内浮动条「本轮已调整 N 处」，支持逐条撤销 / 全部放弃
  → [用户] 点击「接受本轮改动」（浮动条，预览窗口内左上角区域）
  → [系统] 结构化批量清单一次性发给调度员会话（含 PRD 同步指令；
     语音意见按 `- 元素「X」：用户意见「文字」` 附带）
  → [路由] 收到【点选纠错·批量修改】= 用户已收齐，直接委派执行，不再追问（v0.17.54 c3）
  → [视觉] 预览刷新展示新版本；iframe 内 inline 效果与角标/窄条一并清理（undo-all）
```

### 快速选项面板内容（实现）

| 选项 | 图标 | 后续交互 |
|------|------|---------|
| 换个颜色 | 🎨 | 4预设色(红#DC2626/蓝#4F46E5/绿#059669/靛蓝#6366F1) + 🎨自定义调色板(input type=color)，点击后即时应用 |
| 改文字 | 🖊 | 切回会话输入框，元素引用随消息携带，由 Agent 执行替换 |
| 换个位置 | 📐 | 进入拖拽模式，iframe 内拖动，松手偏移入清单（即时生效） |
| 删掉它 | 🗑 | 元素即时 opacity 降低模拟删除，入清单，可撤销 |
| 语音 | 🎤 | 听写结果按 sourceInputId=`ctf-voice-<sessionId>-<elementId>` 精确路由，归属发起时元素（面板关闭/切元素不串，命中即 preventDefault 防双重输出） |
| 其他 | 💬 | 切回会话输入框引导用户描述意图 |
| 取消 | — | 点击面板外区域关闭 |

### 待接受清单与批量接受

| 组成 | 说明 |
|------|------|
| 浮动条 | 定位在预览窗口内左上角（随 iframe 位置 1.5s 轮询跟随），文案「本轮已调整 N 处」+「接受本轮改动」 |
| 撤销 | 逐条撤销（同元素多改按 id 合并，undo 幂等回原始态）；全部放弃（含角标/窄条清理） |
| 角标 | 元素内部右上角（top:2px/right:2px 防溢出裁剪），红色计数，点击看全部意见 |
| 窄条 | 元素下方改动摘要，点击查看意见浮层 |
| 接受 | 批量结构化清单 → 调度员会话直接委派执行 + PRD 同步；成功后 iframe undo-all 清理 |

### 工作区差异（保留 v0.3 基线）

| 维度 | 快消型工作区 | 长期迭代型工作区 |
|------|-------------|----------------|
| 高亮方式 | 独立div覆盖层(`click-highlight`)，2px `--color-primary`边框，`rgba(79,70,229,0.08)`背景 | CSS class `preview-el-highlight`，outline 3px `--color-primary`，outline-offset 2px |
| 选项面板样式 | 含具体元素类型标题(如"对此按钮的操作：")，带"✕"关闭 | 通用标题"你想怎么改？"，底部"取消"按钮 |
| 选项排列 | 纵向列表，每个选项占一行 | 纵向列表，带图标行 |
| 颜色子选项 | 嵌入展开式色板(4色)，可收起 | 直接应用随机主色 |
| 取消方式 | 点击预览空白区域/选项面板"✕" | 点击空白区域/面板"取消"；document级click监听 |
| Agent回复 | "好的，我看到了这个[元素类型]。你想怎么改？" | 同左（带typeLabels映射） |

### 边界Case
- 点击空白背景 → 对话区提示（2秒内连击≥2元素以最后一次为准，重置高亮计时器；快速连击有节流）
- 修改中 iframe 刷新/切换 → 重置选中状态与清单（load 清理随 1.5s 轮询绑定，修复首现挂不上）
- 同元素多次修改 → 按 id 合并，undo 幂等回原始态
- 拖拽误触（<4px，devicePixelRatio 归一）→ 还原不上报；拖后 400ms 抑制 click 误重选
- postMessage 伪造 → 宿主侧校验 e.source===parent + 去重 + 会话级上限 24 条
- 多预览 iframe 并存时取错目标（R2-Y3）→ 已知限制，当前单预览窗口场景未触发（见变更文档遗留表）

### 心理防御文案
- 成功："改好了，你看看效果？不满意随时告诉我。"
- 失败："刚才的修改没有成功，我已经帮你回到上一个正常版本，你的内容没有丢失。我们换个思路试试？"
- 等待超5秒（同交互2的progress字串）

### 与v0.3 spec的差异说明（v0.3→v0.4，以产品实现为准）
> v0.3 描述"点击后对话区追加 Agent 消息→向导Agent转修改规约→编程Agent逐次执行"——实现改为**即时调整+待接受清单+批量接受**（v0.17.48）：换颜色/删掉/换位置在 iframe 内即时生效不与模型逐次交互，用户收齐后一次接受。
> v0.3 描述"颜色 4 预设色"——实现增加 🎨 自定义调色板（v0.17.53）。
> v0.3 未覆盖**语音意见**——实现增加 🎤语音选项，听写结果按元素归属附角标（v0.17.52/54）。
> v0.3 未覆盖**并列展示**——实现增加 ensurePreviewSplit：交互各时机自动转分屏（v0.17.55）。
> v0.3 未覆盖**意见收集轮门禁**——实现增加 prompt 级硬门禁：单条意见只记录+确认+追问，收齐才批量执行（v0.17.51）。
> 快消型/长期迭代型高亮与面板样式差异保留 v0.3 基线描述（见"工作区差异"）。

### 技术基座风险标注
> 基于TypeCClickToFix + TypeFIframePreview，核心链路已验证。跨iframe通信已通过postMessage验证（技术基座R7已消除）。快消型高亮层通过JS computed rect定位实现，长期迭代型通过CSS outline class实现，两种方案均不依赖iframe沙箱。


## 交互2：等待状态与进度反馈

### 触发条件
- 操作开始后超过5秒未返回结果
- 适用范围：原型生成、代码生成、修改执行、测试执行等所有可等待操作
- PRD追溯：§7.5（5秒阈值 + 五类文案）| 技术基座R6（5秒超时触发逻辑未在Demo中实现）

### 步骤序列（基于原型实现）

```
[触发] 操作超过5秒
  → [视觉] 底部固定位置Toast通知出现（非对话流气泡，非进度条，无确定进度条）
      显示旋转spinner + "我正在帮你生成可运行的版本，这个过程只发生在安全环境里，不会影响你的电脑文件。"
      Toast类型: progress，背景--color-info-bg，文字--color-info
  → [5秒内完成] 不显示任何等待提示，直展结果
  → [超过30秒] 追加Toast(--color-warning)"这次操作花了比预期更长的时间，我还在处理中。如果等太久，你可以催我。"
      （原型未实现[继续等待][先跳过]按钮交互，但熔断回滚场景中实现了类似的[换个方案][先跳过这个功能]卡片按钮）
  → [完成] progress Toast移除，替换为结果通知(success/amber类型)
  → [失败] Toast替换为amber色失败通知
```

### 五种Toast类型对应原型实现

| 类型 | 图标 | 精确文案（原型中PRD §7.5原文） | 背景色 | 自动消失 |
|------|------|------|--------|---------|
| progress | 旋转spinner | "我正在帮你生成可运行的版本，这个过程只发生在安全环境里，不会影响你的电脑文件。" | `--color-info-bg` | 否 |
| success | ✓ | "改好了，你看看效果？不满意随时告诉我。" | `--color-success-bg` | 3.5-4秒 |
| error/amber | ⚠ | "刚才的修改没有成功，我已经帮你回到上一个正常版本，你的内容没有丢失。我们换个思路试试？" | `--color-warning-bg` | 3.5秒 |
| rollback | ↩ | "已经回到之前的版本了，一切都在。要继续的话随时告诉我。" | `--color-warning-bg` | 4秒 |
| timeout | ⏳ | "这次操作花了比预期更长的时间，我还在处理中。如果等太久，你可以催我。" | `--color-warning-bg` | 3.5秒 |
| info | ℹ | 自定义消息 | `--color-info-bg` | 3-3.5秒 |

### 与v0.2 spec的差异说明（以原型为准）
> v0.2描述"对话流底部插入进度消息气泡"——原型实际实现为固定底部Toast通知，非对话流气泡。v0.3更新为原型实现。
> v0.2描述"可预估进度→确定进度条"——原型未实现确定进度条，统一使用旋转spinner。v0.3移除"确定进度条"描述。
> v0.2描述"脉冲加载点(三dot交替缩放)"——原型使用旋转spinner(圆环)。v0.3更新为原型实现。
> v0.2 timeout文案"比预期多花了些时间"——原型PRD精确文案"花了比预期更长的时间"。v0.3更新为原型实现。

### 边界Case
- 5秒内完成 → 不显示进度Toast
- 连续多个等待操作 → 后操作覆盖前操作，移除前操作Toast
- progress类型不自动消失，需由完成/失败事件主动移除
- 其余Toast 3.5-4秒自动消失

### 心理防御文案
直接引用PRD §7.5原文五类场景（以原型中精确嵌入的文案为准），见上表"精确文案"列。

### 技术基座风险标注
> 5秒超时触发逻辑在Demo中为手动触发（技术基座R6），集成阶段通过Jotai atom + setTimeout实现。原型中progress Toast手动触发不做自动5秒检测，超时30秒按钮交互仅在熔断场景模拟。


## 交互3：回滚操作

### 触发条件
- 前置：项目存在至少1个快照
- 触发：用户在工具栏点击"历史版本"按钮
- PRD追溯：§7.4 | US-U06（5个GWT场景）
- 关联流程：user-flows.md Flow 4（编程Agent自愈3次失败→熔断→回滚→用户感知）

### 步骤序列（原型已验证统一流程）

```
[触发] 点击"历史版本"
  → [视觉] 右侧滑出面板(360px宽，250ms ease-out)，背景半透明蒙层(--color-overlay)
      快消型：transform: translateX(100%)→translateX(0)，蒙层渐变透明度
      长期迭代型：独立animation slideIn from translateX(100%)
  → [系统] 读取快照清单，时间倒序，人性化时间描述
  → [视觉] 每项显示：
      快消型：时间轴dot + 连线，版本号+时间戳，自然语言描述，"当前版本"标识(文字badge，--color-primary)
      长期迭代型：时间轴节点(圆点 current/historical)，卡片式布局，meta行含时间+badge
      非当前版本显示[回到这个版本]按钮
  → [用户] 点击某旧版本的"回到这个版本"
  → [视觉] 弹出确认弹窗(居中dialog)：
      标题："确定要回到「[版本描述]」吗？"
      正文："不会丢失现在的版本。你随时可以从历史版本中切回来。"
      按钮：[取消][确定回滚]
      弹窗动画：scaleIn (0.92→1.0) overlay
  → [用户确认]
  → [系统] 先自动保存当前版本为新快照("回滚前自动保存") → 恢复到所选版本 → 刷新时间轴
  → [视觉] 面板保持打开 + Toast(--color-warning)"已回到「[版本描述]」。你随时可以从历史版本中切回来。"
```

### 与v0.2 spec的差异说明（以原型为准）
> 确认弹窗正文：原型为"不会丢失现在的版本。你随时可以从历史版本中切回来。"——v0.2缺少"你随时可以从历史版本中切回来"。v0.3更新为原型。
> 回滚成功Toast：原型为"已回到「[版本描述]」。你随时可以从历史版本中切回来。"——v0.2为"已经回到之前的版本了，一切都在。"。v0.3更新为原型。
> 快消型Toast类型rollback(amber背景，4秒自动消失)，v0.2未明确。

### 边界Case
- 无快照 → 面板显示"暂无历史版本" + "当你确认方案或进行重要修改时，系统会自动保存版本。"（快消型增加空状态图标○）
- 连续回滚 → 每次自动保存当前版本，可无限回滚（原型已验证unshift快照逻辑）
- 回滚出错 → Toast amber色通知
- 无手动快照入口，纯线性列表，无分支UI

### 自愈流程关联
> 编程Agent自愈3次失败→熔断触发时（user-flows.md Flow 4），系统自动执行本交互的回滚步骤，用户感知为：对话区出现安抚消息卡片（含[换个方案][先跳过这个功能]按钮）+ 工作区恢复到上一健康版本。回滚由系统自动触发，非用户手动操作。

### 技术基座风险标注
> 自动快照触发机制未在Demo中验证（技术基座R2），集成阶段通过Jotai+chokidar实现。用户手动回滚的UI交互链已在TypeDTimeline中验证。


## 交互4：角色切换过渡

### 核心原则
用户始终只面对一个Agent。后台静默切换，UI自然过渡。快消型隐于后台，长期迭代型跳到前台。
PRD追溯：§4.3 | US-G06（5个GWT场景）| 技术基座R4（角色切换UI表现未在Demo中验证）

### 通用层

```
[触发] 路由层检测阶段转换
  → [系统] 加载新角色System Prompt+模型(500ms内完成)，保持对话上下文连续
  → [视觉] 状态栏文案淡入淡出(300ms)：
      快消型："AI正在了解你的需求…"（单段式，固定文案）
      长期迭代型：双段式——"[阶段名] | 正在了解你的项目需求…"（阶段名+进度描述）
  → [视觉] 回复风格渐变：需求分析师(开放式提问)→UI/UX(展示预览)→架构师(建议句式)→工程经理(规划句式)
```

### 长期迭代型特有

```
架构设计师跳到前台：
  → 对话流插入内嵌确认卡片（card-in-chat样式，左侧4px --color-primary边框）
  → "技术方案建议" + 通俗语言+选项+优缺点 + [确认方案][我有不同想法]
  → 确认后Toast"已确认：xxx"

工程经理跳到前台：
  → 对话流插入内嵌确认卡片
  → "开发计划" + Sprint拆分+可调优先级 + [可以，开始做吧][我想调整优先级]
  → 确认后Toast"已确认：xxx"
```

### 快消型特有

```
架构设计师/工程经理隐于后台：
  → 状态栏"AI正在了解你的需求…"（静态，无动画）
  → 不产生新消息，不弹出交互，全程自动
```

### 与v0.2 spec的差异说明（以原型为准）
> 状态栏：v0.2描述统一"正在进行…"→"正在设计…"→"AI正在设计方案…"等动态渐变文案。原型中：
>   快消型状态栏为固定文案"AI正在了解你的需求..."，无动态切换；
>   长期迭代型状态栏为双段式("需求分析 | 正在了解你的项目需求…")，阶段名+进度描述，但同样为静态。
> v0.3保留动态渐变的设计意图，但以原型静态实现为当前基线，标记动态效果为集成阶段实现。
> 长期迭代型原型增加"文档面板"（左侧弹出式文档树），属于角色切换架构师阶段后用户可见的新UI元素，v0.2未覆盖。

### 边界Case
- 切换失败 → 保持当前角色，后台重试3次(间隔5秒)，用户无感
- 用户快速连续确认多阶段 → 排队顺序执行
- 切换发生在用户输入时 → 不打断输入
- 阶段回退 → 状态栏回退，对话区"好的，我们回到需求阶段"

### 技术基座风险标注
> 角色切换UI表现未在Demo中验证（技术基座R4）。当前交互设计基于React状态管理+Jotai阶段路由的可行方案，具体过渡动画和状态栏文案映射在集成阶段实现。原型中状态栏为静态文案。
