## 0. 文档定位与适用范围

本文档定义**开发本平台自身**过程中，各角色（人类开发者、向导Agent团队、编程Agent团队、裁判Agent、人类审查者）的**协作流程**与**交互规则**。它回答四个问题：

1. 一份**文档**如何从草稿走到「已确认」？
2. 一段**代码**如何从分支走到「合并入主干」？
3. 一个 **Sprint** 如何从计划走到回顾？
4. 一次**异常/阻塞**如何被自愈、如何被升级？

> ⚠️ 现实约束：本项目处于 Phase 1（MVP）开发期，平台运行时的裁判Agent尚未实现。因此本阶段所有「裁判Agent门禁」「洁净室评审Agent」由**人类开发者 + 校验脚本**模拟执行（参见设计阶段文档清单§四）。随 Phase 2/3 裁判引擎落地，模拟角色逐步替换为真实 Agent，本流程的执行者字段同步更新，流程结构不变。流程先行、实现渐进——这正是本平台"文档即约定"原则的自举应用。

## 1. 角色与职责（RACI 概览）

| 角色 | 所属 | 核心职责 | 本阶段实现形态 |
|------|------|---------|--------------|
| **人类开发者（2-3人）** | 团队 | 拆解任务、最终决策、跨模块协调、模拟裁判与评审 | 真人 |
| **Commander（指挥官）** | 协作层 | 任务分解、分发、阻塞升级受理点、全局一致性 | 真人 + Agent 辅助 |
| **Worker Agent** | 协作层 | 承接单一产出任务（文档/代码），自审后交付 | Agent |
| **向导Agent团队**（需求分析师/UI-UX顾问/架构设计师/工程经理） | 文档域 | 产出 PRD/UX/架构/规划文档 | Agent（见 [[03_ARCHITECTURE/architecture.md]] §8 模型映射） |
| **编程Agent团队**（全栈/前端/后端/测试/代码审查员/架构师） | 代码域 | 编码、自审、交叉审查、GWT 测试 | Agent |
| **评审Agent（洁净室）** | 质量域 | 对照 G1-G5 多轮技术评审，**只出意见不改文档** | Agent（本阶段人类+脚本模拟） |
| **裁判Agent** | 门禁 | 硬约束+软约束综合判定，通过/退回 | Agent（本阶段人类+脚本模拟） |
| **人类审查者/产品负责人** | 决策域 | 人机交互评审最终拍板，文档状态「待审→已确认」 | 真人 |

**洁净室原则**（贯穿全文）：评审Agent、裁判Agent 与产出Agent 使用不同 System Prompt / 不同人，**不得直接修改产出物**，只能输出意见或判定。产出方据此自行修改。这是独立审查有效性的根本保证。

## 2. 核心工作流①：文档产出 → 评审 → 确认

> 严格对齐 `设计阶段-文档产出清单与质量标准.md §1.4` 两阶段评审流程。

### 2.1 输入 / 执行者 / 动作 / 输出链

| 阶段 | 输入 | 执行者 | 动作 | 输出 |
|------|------|--------|------|------|
| 产出 | 上游已确认文档（如 PRD）+ 文档清单条目 | Worker Agent（产出方） | 按清单「核心内容/质量门槛」撰写草稿，元信息头齐全 | 状态=`草稿` 的文档文件 |
| 第一阶段·评审 | 草稿文档 | 评审Agent（独立） | 对照 G1-G5 逐项检查，输出评审意见（不改文档） | 评审意见清单 |
| 第一阶段·修改 | 评审意见 | Worker Agent（产出方） | 逐条回应/修改 | 修订稿 |
| 第一阶段·收敛 | 修订稿 | 评审Agent | 第二/三轮验证，确认未引入新问题；**输出最终报告后自动触发§2.3 第二阶段** | 最终技术审查报告（通过项/遗留项） |
| 第二阶段·人机评审 | 技术审查报告 + 文档 | 人类审查者 + Agent | 人类标注关注点 → Agent 回应/修改 → 多轮交互 | 标注意志 + 修订 |
| 确认 | 达到「可接受/满意」 | 人类审查者 | 明确表态 | 状态=`已确认` ✅ |

### 2.2 第一阶段：Agent 团队洁净室评审（自动，G1-G5）

| 门禁 | 检查内容 | 不通过处置 |
|------|---------|-----------|
| **G1 完整性** | 必填章节齐全、元信息完整、依赖文档已就绪 | 红色问题，必改 |
| **G2 一致性** | 与 PRD 及其他已确认文档无逻辑矛盾 | 红色问题，必改 |
| **G3 可执行性** | 描述可被下一阶段直接使用（编码/测试可开工） | 红色问题，必改 |
| **G4 可读性** | 结构清晰、术语一致、图表有标注 | 黄色建议 |
| **G5 格式合规** | 命名/元信息/`[[引用]]` 规范（清单§1.1-1.3） | 红色问题，必改 |

**收敛规则**：G1-G5 全部无红色问题（允许黄色建议项）方可进入第二阶段。**评审—修改循环最多 3 轮**；第 3 轮仍有红色问题 → **升级至人类审查者仲裁**（见§5.1「文档评审不收敛」行）。

### 2.3 第二阶段：人机交互评审

人类审查者阅读「文档 + Agent 评审报告」，标注疑问 → Agent 逐条回应或修改 → 人类复审 → 往复至人类明确表示「可接受」或「满意」。**只有人类有权将状态从「待审」改为「已确认」。** Agent 不得自行标记已确认。

### 2.4 流程图

**图 2-1　文档产出 → 评审 → 确认流程**

```text
草稿(产出Agent) ──▶ 洁净室评审(G1-G5,评审Agent,≤3轮)
                         │ 红色问题未清?──是──▶ 迭代修改(产出Agent) ──┐
                         └ 否                                              │
                         ▼ <───────────────────────────────────────────────┘
                  人机交互评审(人类+Agent,多轮)
                         │ 人类不满意?──是──▶ 修改(产出Agent) ──┐
                         └ 否                                   │
                         ▼ <────────────────────────────────────┘
                     已确认 ✅ (人类拍板)
```

## 3. 核心工作流②：编码 → 审查 → 测试 → 合并

> 对齐 PRD §6.2 长期迭代型流程、§4.5 测试/裁判职责边界、§9 裁判机制。
> 本流水线为通用结构（覆盖快消型/长期迭代型）；本项目 MVP 激活的具体角色、模型绑定与 ③′ 修订细节见 [[05_PROJECT_PLAN/team-config.md]] §3。

### 3.1 流水线（输入/执行者/动作/输出）

| 步骤 | 输入 | 执行者 | 动作 | 输出 |
|------|------|--------|------|------|
| ① 编码 | 已确认架构/API/GWT 文档 + Sprint 任务卡 | 编程Agent（全栈/前端/后端） | 按 PlantUML 类图与 API Spec 实现，代码结构 ≡ PlantUML | 特性分支代码 |
| ② 自审 | 特性分支代码 | 编程Agent（产出方自审） | 静态检查、命名、安全、合规自检 | 自审通过/自改 |
| ③ 交叉审查 | 自审后代码 | 代码审查员（独立）+ 人类 | 对照 PlantUML/类图一致性、PRD 功能覆盖，**只出意见不改代码** | Review 意见 |
| ③′ 修订 | Review 意见 | 编程Agent（产出方） | 逐条回应/修改后**重提③交叉审查** | 修订稿 |
| ④ 测试 | 审查通过代码 | 测试Agent | 跑全量 GWT Feature（正常+边界+异常），输出通过率；**全量通过→进⑤，存在失败→回③′修订** | 测试报告 |
| ⑤ 裁判判定 | 测试报告 + 代码 + 文档 | 裁判Agent | 硬约束（结构≡PlantUML？PRD功能全有GWT？API端点Schema齐？）+ 软约束（逻辑/可测/完整/可读） | 通过 / 退回+问题清单 |
| ⑥ 合并 | 裁判通过 | Commander/人类 | 合并入主干，触发快照 | 合并提交 + 健康快照 |

### 3.2 异常自愈子流程（对齐 PRD §6.3）

编码/构建/测试**失败**时，编程Agent 自主决策修复策略，**最多 3 次**：

**图 3-1　编码异常自愈子流程**

```text
失败 ──▶ 自动修复(≤3次,每次可换策略)
              ├── 成功 ──▶ 继续流水线
              └── 3次仍失败 ──▶ 熔断触发 ──▶ 回滚上一健康快照
                                            │
                                            ▼
                                  告知用户(心理防御文案)
                                            │
                          ┌─────────────────┴──────────────────┐
                          ▼                                      ▼
                    快消型:换技术方案重试              长期迭代型:涉及设计约束不可实现?
                    (编程层闭环,不倒回需求)                  ├── 是 ──▶ 出具变更说明 ──▶ 用户确认 ──▶ 调整方案
                                                          └── 否 ──▶ 换方案重试
                          【全链路不倒回需求阶段】
```

### 3.3 裁判门禁要点（对齐 PRD §9）

- **硬约束**（不可通融，不通过直接退回；完整集见 PRD §9.2，此处举要）：PRD 必填项、PlantUML 语法/类关系、API 端点 Schema、Sprint ≤2周粒度、Team Config 角色职责、GWT 文件存在性、**代码结构 ≡ PlantUML 类图**。
- **软约束**（AI 评估，给通过/建议/退回）：逻辑一致性、可测试性、完整性、可读性。
- **退回次数上限**：快消型 ≤2 次（超过 → 人工介入提示）；长期迭代型 不限（必须通过）。**退回后流向**：一律走 ③′ 修订→重提 ③→④→⑤；长期迭代型多次退回且涉及设计约束不可实现时，转 §5.3 架构变更说明路径，不无限循环。
- **裁判只管交接是否到位，不审代码质量细节**——那是代码审查员的职责（PRD §9.1）。

## 4. 核心工作流③：Sprint 周期（计划 → 执行 → 评审 → 回顾）

> 对齐 PRD §14 路线图、设计阶段 DOC-5.1。每 Sprint ≤ 2 周，交付可运行增量。
> 具体 Phase/Sprint 拆解（Phase 1 = S1-S3、纵向切片、依赖拓扑）见 [[05_PROJECT_PLAN/sprint-plan.md]]；本节只定义 Sprint 内部的协作节奏，不规定具体 Sprint 内容（属 sprint-plan 职责）。

| 阶段 | 输入 | 执行者 | 动作 | 输出 |
|------|------|--------|------|------|
| **计划会议** | 路线图 + 待办 + 容量 | 全员 + Commander | 选定本 Sprint 用户故事，拆任务卡，估点，认领，定义 DoD | Sprint Backlog + 任务卡 |
| **执行** | Sprint Backlog | Worker Agents / 开发者 | 并行推进文档流(§2)与代码流(§3)；每日同步进度/阻塞 | 增量产物 + 每日状态 |
| **评审（Sprint Review）** | 本 Sprint 增量 | 全员 + 产品负责人 | 演示可运行增量，裁判/人类验收 DoD | 验收结论 + 待办调整 |
| **回顾（Retrospective）** | 本 Sprint 全程 | 全员 | 做/不做/改进三栏；提炼可复用流程改进 | 改进项 → 下 Sprint 计划 |

**节奏纪律**：Sprint 间不循环依赖；增量必须可运行（不是"完成 50% 文档"）；阻塞必须在每日同步暴露，不得捂到评审日。

## 5. 核心工作流④：异常处理与升级

本节定义**阻塞**识别、**升级**阈值、回滚触发、架构决策升级四类规则。

### 5.1 阻塞识别与升级路径

| 阻塞类型 | 识别信号 | 一级处理 | 升级阈值 | 升级目标 |
|---------|---------|---------|---------|---------|
| 任务阻塞 | Worker 无法独立推进（缺依赖/权限/信息） | 自查 .context + 上下文 30 分钟 | 静默 ≥2 小时无进展 | Commander（重新分发/补依赖） |
| 文档评审不收敛 | 洁净室第 3 轮仍有红色问题 | 产出方+评审方对齐 | 第 3 轮未过 | 人类审查者仲裁 |
| 裁判退回超限 | 快消型退回超过 2 次（即第 3 次触发） | 编程Agent 换方案 | 超过 2 次 | 人工介入提示 |
| 跨模块冲突 | 两份文档/代码对同一概念描述矛盾 | 当事 Worker 协商 | 协商 1 轮未决 | Commander 裁定一致性基准 |
| 模型/API 不可用 | 编程Agent 主模型失败 | 切备选（见 [[05_PROJECT_PLAN/team-config.md]] §4 降级矩阵 / 架构§8） | 备选亦失败 | Commander + 人类评估降级方案 |

**升级纪律**：升级时必须携带「已尝试的方案 + 失败原因 + 建议方向」，禁止"裸抛"问题。

### 5.2 回滚触发条件（对齐 PRD §6.3、§7.4）

触发回滚的**明确条件**（任一满足即触发）：

1. 编程Agent 自修复 **3 次仍失败** → 熔断回滚。（触发者：编程Agent 自熔）
2. 用户**主动撤销**（PRD §7.4 / 埋点事件#6）→ 回滚到指定快照。（触发者：用户）
3. 合并后发现**回归**（原通过的 GWT 用例失败，合并后 24h 内或下个 Sprint 评审前发现）→ 回滚合并提交。（触发者：测试Agent / 人类）
4. 模式转换（快消→长期，PRD §7.4）→ 转换前自动留快照。（触发者：系统自动）

**回滚不丢当前**：当前状态也存为快照（PRD §7.4）。**只做线性回滚，不做分支**——零基础用户无需理解分支。

### 5.3 架构决策升级机制

当编程Agent 发现**涉及设计约束不可实现**（如某 PlantUML 关系无法落地），不得擅自改架构，也不得倒回需求阶段，而走**变更说明**路径：

**图 5-1　架构决策升级流程**

```text
发现设计约束不可实现
   │
   ▼
编程Agent 出具变更说明(原因 + 影响范围 + 替代方案)
   │
   ▼
升级至架构设计师 + 人类审查者评估
   │
   ├── 替代方案可接受 ──▶ 用户确认 ──▶ 更新 PlantUML/架构文档(走§2文档流) ──▶ 继续编码
   └── 不可接受 ──▶ 回滚 ──▶ 重新设计该模块
```

**红线**：任何对已确认架构文档（`03_ARCHITECTURE/*`）的修改，必须重走文档产出→评审→确认流程（§2），不得在代码里"先改了再说"。

## 6. 协作交互通用规则

1. **任务交接以文件为准**：Agent 间通过项目目录交接（架构§9），不靠口头/聊天记忆。每个交付物是磁盘上的文件。
2. **可见进度**：多步任务用 todo 追踪；开始/完成即时更新状态。
3. **brief_echo 复述**：承接任务时先复述理解，确认无误再动手，防止偏差。
4. **不越权**：Worker 不改架构红线、评审方不改产出物、Agent 不自行标"已确认"。
5. **失败要上报**：测试失败、自修复熔断、裁判退回必须如实报告，不得隐瞒或粉饰。
6. **元信息与引用**：所有文档遵循清单§1.1-1.3，`[[引用]]` 指向真实存在的文件。
