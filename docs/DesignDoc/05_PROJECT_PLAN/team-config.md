## 0. 文档定位与边界

本文定义**开发平台本身**过程中所激活的**编程Agent团队**角色配置——回答"B 层实现时该激活哪些编程Agent角色、各绑定什么模型、如何协作"。

**三条边界（防歧义）**：

1. **是"开发平台本身"的团队，不是"运行时为用户项目创建的团队"**。后者由向导Agent的工程经理角色在运行时按工程模板动态推断（见 [[03_ARCHITECTURE/architecture.md]] §10），不在本文范围。
2. **范围限定编程Agent团队**。向导Agent团队（需求分析师 / UI-UX顾问 / 架构设计师 / 工程经理）与裁判Agent（独立模块）的配置见 [[03_ARCHITECTURE/architecture.md]] §8，不在本文激活清单内；但裁判Agent作为门禁协作方出现在 §3 协作流程中（§3 已先于 M2 完整产出，详见本文 §3）。
3. **只做取舍与细化，不重复 arch §8**。§8 已给出 13 个角色的模型-角色映射与数据等级，本文据此判定**哪些在 MVP 激活、哪些预留 Phase 2-3**，并细化职责边界与协作。

**自举说明**：平台用自己的多智能体方法论开发自己（见 [[05_PROJECT_PLAN/workflow.md]] §0），故本文配置的编程Agent团队真实参与平台代码的编码、审查、测试全流程，非纸面摆设。

## 1. 本项目类型判定

| 判定维度 | 结论 | 依据 |
|---------|------|------|
| 项目形态 | **桌面应用**（Electron ^39.5.1 + React ^18.3.1 + TypeScript，基于 Proma fork） | arch §1.1 |
| 模板匹配 | **"桌面工具"模板** | PRD §11.3 关键词"电脑工具/桌面软件"→桌面工具；arch §10 推断规则同 |
| 模板预设团队 | **全栈 + 测试**（桌面工具模板基线 ＝ 快消型最小集） | PRD §11.2 桌面工具行；arch §10（"快消型统一使用'桌面工具'模板（最小集）"） |
| 开发模式 | **长期迭代型**（非快消型） | 主据：PRD §3.2 定义长期迭代型为"需持续更新版本的项目 ＋ 完整软件工程方法论驱动"，本平台为课题交付物、按 PRD §14 Phase 1–4 持续迭代 → 符合定义；辅证：已具完整文档体系 01–07/PlantUML/Sprint/版本管理 |
| 数据等级基线 | MVP 激活角色优先选 L3/L2 实测或强推断项 | arch §8 数据等级说明 |

**判定结论**：

> 本项目 = **"桌面工具"模板（基础集）× 长期迭代型开发模式**。

由此推导 MVP 激活团队的结构：

- **快消型最小集**（桌面工具模板基线，任何模式都用）：`全栈开发 + 测试工程师`
- **长期迭代型增量**（因平台按完整方法论开发而追加）：`+ 代码审查员`
- **Phase 2-3 预留**（不为"可能有用"提前激活，见 §5）：`架构师 / 前端·后端拆分 / DevOps工程师 / 项目经理`

### 2.2 激活判定的关键取舍说明

**前置澄清：如何解读 arch §8 的"P0/P1"与"Phase X 激活"两类标注（化解一致性歧义）**

arch §8 的依据列对编程Agent角色同时给出两类标注，二者维度不同、不可混用：

- **P0 / P1**：角色池内的**优先级层级**（资源倾斜、相对重要性参考），**不是激活时序**。如"架构师 = P0"指其在角色池中重要性最高，并非"必须最先激活"。
- **"Phase X 激活" / 条件标注**（长期迭代型激活 / 有 UI 需求时激活 / 需部署时激活 …）：这才是**激活时序与条件**的权威判定依据。

下文所有取舍均以"Phase X 激活 / 条件标注"为激活判定准绳，P0/P1 仅作资源参考。

1. **为何 MVP 不拆"前端 + 后端"而用"全栈"**：桌面工具模板预设即"全栈"（PRD §11.2）；平台渲染层与主进程同为 TypeScript、同进程，全栈开发可一体覆盖。前后端拆分属"有 UI/后端需求时激活"的条件角色，MVP 单全栈已覆盖，拆分即"可能有用"→ 不激活（守 DOC-5.2"无冗余"门禁）。
2. **为何代码审查员进 MVP（化解 §8"P1 角色"标签）**：§8 标代码审查员为"P1 角色，长期迭代型激活"——按前置澄清，"P1"是池内优先级（非时序），"长期迭代型激活"是激活条件且**无 Phase 门禁**。本项目为长期迭代型（§1）→ 条件命中 → 激活。再叠加：PRD §4.4"代码审查员 = 长期迭代型必选"、[[05_PROJECT_PLAN/workflow.md]] §3.1 设独立"③ 交叉审查"步骤、洁净室原则禁产出方自审 → 不可替代，入 MVP。
3. **【§2.2.3】为何架构师不进 MVP、推迟到 Phase 2（化解 §8 多重标注）**：§8 给架构师的多重标注——"P0 + 长期迭代型必选 + Phase 2 激活"三类时序/优先级标签（另含职责描述"负责审核 PlantUML 规约与代码一致性"）——看似矛盾："P0 + 必选"推其尽早激活，"Phase 2 激活"又推迟它。按前置澄清，**"Phase 2 激活"是激活时序的权威判定**，"P0 / 必选"描述其激活后的重要性与强制性，而非要求在激活前提未达时提前激活。架构师（编程Agent内）的核心职责是"审核 PlantUML 规约与代码一致性"，该职责以 PlantUML 作为强约束层落地为前提；PRD §14 将 PlantUML 编程与校验规划在 Phase 2（Phase 1 / 快消型 PlantUML 可省略或极简，见 PRD §3.1 / §8.2）。故 MVP 阶段该角色无足量工作负载，激活即"可能有用"→ Phase 2 预留。MVP 期间的架构一致性由"人类开发者（架构决策）＋ 代码审查员（审查中兼顾结构）"过渡承担。
4. **【§2.2.4】裁判Agent 为何不在激活清单**：裁判Agent 是**独立模块**（arch §8 / PRD §4.1），不属于编程Agent团队；且 Phase 1 平台运行时尚未实现，由"人类 + 脚本"模拟（workflow.md §0 / §1）。其配置归属运行时裁判引擎，本文仅在 §3 协作流程中作为门禁协作方引用，模型绑定（deepseek-v4-flash）见 arch §8。

> **跨文档协调注（v0.2 新增，对应 Y-G2-3）**：sprint-plan S3（编程收口闭环）当前未单列"交叉审查"独立步骤，故本文 §2.1 将代码审查员列入 MVP 激活的 Sprint 落点以 sprint-plan 为准——若 S3 未排独立交叉审查步骤，MVP 期间由人类审查者对照 [[01_PRD/prd.md]] §4.4 模拟（对齐 workflow §0 现实约束）。此为跨文档协调项，待 sprint-plan 转"已确认"时双向收敛，不构成本文内部矛盾。

## 3. 角色间协作流程（MVP 激活集）

本节定义 MVP 激活的 3 个编程Agent角色（全栈开发 / 测试工程师 / 代码审查员）之间的协作链，以及与裁判Agent（门禁协作方）的交接。流程结构与 [[05_PROJECT_PLAN/workflow.md]] §3.1 编码流水线一致；因 MVP 不拆前后端，省略"前端/后端并行"分支。

### 3.1 编码流水线

| 步骤 | 输入 | 执行者（模型） | 动作 | 输出 |
|------|------|--------------|------|------|
| ① 编码 | 已确认架构/API/GWT 文档 + Sprint 任务卡 | 全栈开发（GLM 5.1） | 按 PlantUML 类图（Phase 2 起为强约束）与 API Spec 实现渲染层 + 主进程服务/引擎 | 特性分支代码 |
| ② 自审 | 特性分支代码 | 全栈开发（GLM 5.1） | 内部静态自检：命名、安全、合规 | 自审通过 / 自改 |
| ③ 交叉审查 | 自审后代码 | 代码审查员（GLM 5.1，独立） | 独立审查安全（沙箱逃逸 / prompt 注入）、合规、结构一致性；**只出意见不改代码** | Review 意见清单 |
| ③′ 修订 | Review 意见 | 全栈开发（GLM 5.1） | 逐条回应 / 修改 | 修订稿 |
| ④ 测试 | 审查通过代码 | 测试工程师（GLM 5.1，轻量场景备选 flash） | 跑全量 GWT Feature（正常 + 边界 + 异常），输出通过率 | 测试报告 |
| ⑤ 裁判判定 | 测试报告 + 代码 + 文档 | 裁判Agent（deepseek-v4-flash；**Phase 1 由人类 + 脚本模拟**——规范对齐 workflow §0：硬约束用 PRD 必填项 / GWT 存在性 / API Schema checklist 机检，软约束由人工判定） | 硬约束（PRD 必填项 / PlantUML 语法 / API Schema / Sprint 粒度 / 角色职责 / GWT 存在性 / 代码 ≡ PlantUML）+ 软约束（逻辑 / 可测 / 完整 / 可读） | 通过 / 退回 + 问题清单 |
| ⑥ 合并 | 裁判通过 | 人类开发者（Commander 属协作层、**非编程Agent激活角色**，见 workflow §1 RACI） | 合并入主干，触发健康快照 | 合并提交 + 快照 |

### 3.2 异常自愈子流程（对齐 PRD §6.3 / workflow.md §3.2）

编码 / 构建 / 测试**失败**时，编程Agent自主决策修复策略，**最多 3 次**：

```text
失败 → 自动修复(≤3 次, 每次可换策略)
          ├ 成功 → 继续流水线
          └ 3 次仍失败 → 熔断 → 回滚上一健康快照 → 告知用户(心理防御文案)
                                ├ 快消型: 换技术方案重试(编程层闭环)
                                └ 长期迭代型: 涉设计约束不可实现 → 出具变更说明 → 用户确认 → 调整方案
       【全链路不倒回需求阶段】
```

### 3.3 与裁判Agent的职责边界（对齐 PRD §9.1）

- **裁判Agent 是流程门禁，不是质量审计员**：只查"交接是否到位"（测试全过？PRD 功能全有 GWT 对应？代码结构 ≡ PlantUML？API 端点 Schema 齐？），**不深入审计代码质量细节**。
- **代码质量细节归代码审查员**（步骤 ③）。二者分工不可混淆：裁判判"能不能过门"，审查员判"代码好不好"。
- **退回次数上限**：快消型 ≤ 2 次（超则人工介入提示）；长期迭代型不限（必须通过）。本项目为长期迭代型 → 不限退回，必须通过。

### 3.4 自举说明

本流水线是**平台开发自身**的编码流水线（自举），与平台运行时为用户项目驱动的流水线（[[01_PRD/prd.md]] §6）**结构一致、执行者同源**——这正是"文档即约定"原则的自举验证（workflow.md §0）。Phase 1 平台运行时裁判Agent未实现，步骤 ⑤ 由"人类 + 脚本"模拟，随 Phase 2/3 裁判引擎落地逐步替换为真实 Agent，流程结构不变。

## 4. 备选模型降级策略

### 4.1 降级矩阵

| 角色 | 主模型 | 一级降级 | 二级降级 / 升级 | 依据 |
|------|--------|---------|---------------|------|

| 测试工程师 | GLM 5.1 | **flash**（轻量测试场景） | **deepseek-v4-flash** | arch §8（备选 flash）+ 备选策略 |
| 代码审查员 | GLM 5.1 | **deepseek-v4-pro**（强推理，适合审查） | 备选亦失败 → 升级 Commander + 人类 | 主绑定 GLM 5.1 与 §8 一致；备选 deepseek-v4-pro 为**本文推导**（§8 备选策略句仅显式覆盖全栈/测试，未覆盖代码审查员；审查重推理故选之） |

> **术语注（v0.2 新增，对应 Y-G2-1）**：arch §8 所称 "flash"（测试工程师 / DevOps 备选）= deepseek-v4-flash（轻量推理模型）。本文 §2.1 / §3.1 / §4.1 中的 "flash" 与 "deepseek-v4-flash" 同义，统一指 deepseek-v4-flash。

### 4.2 降级原则

1. **不跨数据等级随意降级**：L3 实测项（全栈开发）降级至 L1 通用推理项（deepseek-v4-pro 标 L1 待测）时，须回归关键 GWT 验收确认质量未塌方。
2. **降级须留痕**：每次模型切换记入埋点（PRD §12.4 事件 #9 编程Agent执行），便于复盘。
3. **升级纪律**：备选模型亦失败时，按 workflow.md §5.1 升级，**必须携带"已尝试方案 + 失败原因 + 建议方向"**，禁止裸抛问题。

### 4.3 Phase 2/3 角色的 Proxy 降级

arch §8 注明：Phase 2/3 激活的角色可在集成阶段通过 **Proxy 降级**复用已有模型（无需为新角色单独配置未验证模型）。本文 §5 预留角色落地时遵循此机制。
