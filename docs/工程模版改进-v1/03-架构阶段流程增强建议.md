# 架构阶段流程增强建议（给平台侧，不动代码）

> 版本：v1.0-draft | 日期：2026-09-18
> 上游依据：`00-现状差距分析.md`（G2/G3/G4/G7）、`02-Spike实验协议.md`
> 性质：**建议条文**，供平台迭代参考；本目录未修改任何平台代码或现有文档。
> 目标：把"架构师在模版知识不足时现场踩坑"升级为"主动补环境知识 + 派 Spike 实验 + 产物工程化沉淀"，使开发与测试阶段直接继承架构阶段的实验资料和环境。

---

## 1. 架构师任务书注入（模版知识如何进架构师上下文）

建议在架构阶段生成架构师任务书时，注入以下五件（条文形式）：

| # | 注入物 | 内容 | 来源 |
|---|--------|------|------|
| J1 | 品类模版全文路径 | `nanju-engineering-templates/<品类>.md`（v2 后为改进版），并指令"必读 §2 组件环境清单与 §7 坑库" | 模版分发机制（既有） |
| J2 | 环境探测证据 | 项目开始时执行模版 §2.3 `check_env` 脚本的 JSON 输出，作为架构师的"已知环境事实" | 新增 |
| J3 | Spike 派发权声明 | 明示架构师有权按 `02-Spike实验协议.md` 派子会话实验，含时间盒与产物规范 | 新增 |
| J4 | 触发判据 | 协议 §2 的 T1/T2/T3 三条（知识缺口/决策影响/可时间盒） | 新增 |
| J5 | 产物落位指令 | 实验产物一律落工程目录 `00_SPIKES/`，索引 `00_SPIKES/INDEX.md` | 新增 |

**理由** [实证映射]：昨晚架构师不知道"XKB 注入边界 / ASR 端点 / 回环测试方案"，因为 J1-J5 均不存在——模版里没有（G1/G3），任务书里也没有（G4）。注入 J2 的意义：环境事实（有无可麦克风、有无 X 会话）先于架构决策，而不是 8 轮验收中才发现。

## 2. Spike 触发时机与执行流（何时触发）

建议架构阶段增加两个检查点（条文）：

**CP-A 环境普查点（架构设计开始前）**
- 执行品类模版 §2.3 探测脚本 → 产出 `env_probe.json`
- 对照模版 §2 组件清单：缺失的"必须"级组件 → 决定安装或选降级替代，写入架构文档"环境约束"节
- 对照 §7 坑库：涉及 [推断待验证] 条目且命中本项目的坑 → 标记为候选 Spike

**CP-B 方案验证点（架构方案敲定前）**
- 对每个关键技术决策跑 T1/T2/T3 判据；命中即派 Spike（可并行多个子会话）
- Spike 未决前，架构文档中该决策点标注 `PENDING(SPIKE-NNN)`，不得写成确定性结论
- 全部 Spike 验收后，架构文档更新结论并把 `PENDING` 替换为结论引用

## 3. Spike 产物如何进 engineering.json 与 06_TESTS

### 3.1 engineering.json 增补字段（建议 schema）

```json
{
  "spikes": [
    {
      "id": "SPIKE-001",
      "slug": "x11-cjk-injection",
      "question": "XkbSetMap 注入 CJK 对 GTK 应用是否生效",
      "verdict": "confirmed|refuted|partial",
      "artifacts": ["00_SPIKES/spike-001-x11-cjk-injection/"],
      "report": "00_SPIKES/spike-001-x11-cjk-injection/README.md",
      "evidence": ["evidence/xkb_probe.json"],
      "decided_by": "architect-session-id",
      "ts": 1730000000000
    }
  ],
  "env_probe": "env_probe.json",
  "knowledge_gaps_pending": []
}
```

### 3.2 06_TESTS 引用规则（验收证据链）

- 每条验收项（GWT 或测试用例）新增可选字段 `evidence_ref`：指向 `00_SPIKES/.../evidence/*` 或 `drivers/` 产物
- 验收判读优先级：**evidence_ref 文件 > 驱动脚本重跑 > 会话口头陈述**
- 建议判据 [根因映射]："8 轮才部分收敛"的本质是验收证据链缺失。若每个验收项都有 evidence_ref，收敛轮次应显著下降（该效果待后续项目对照验证 [推断]）

### 3.3 开发/测试阶段继承

- 开发任务书注入：`00_SPIKES/INDEX.md` 路径 + 相关 Spike 的 README（结论段）
- 测试任务书注入：相关 Spike 的 `drivers/` 脚本可直接作为测试驱动底稿（"实验资料和环境留给后面的开发和测试"的落地 [父会话根因判断原文]）

## 4. 模版知识回填与版本维护（平台级闭环）

| 条文 | 内容 |
|------|------|
| R1 | 项目验收收敛轮次 > 3 时，强制复盘会话：逐条列出"当时模版里没有的知识" → 回填品类模版 §2/§5/§7，Bump Minor（依据：`01-模版结构规范-v2.md` §6） |
| R2 | Spike 结论回填时必须带证据等级标注与来源 Spike 编号（如 `来源：SPIKE-001，2026-09-17`） |
| R3 | 模版源头（nanju-guide 09_工程模板）与运行时快照（nanju-engineering-templates）同步更新并同版本号 |
| R4 | S8 文档勘误：sprint-plan L322 的"6 模板（Web/移动/桌面/CLI/**硬件**/AI）"应更正为 api-backend，与实际交付对齐 [文证：`../00-现状差距分析.md` §7] |

## 5. 向导/工程经理侧配套（最小集）

- 品类推断后向用户透明展示一句"将按〈品类〉工程标准执行"（PRD §11.3 要求对用户不可见的是推断过程，不排斥结果可解释）[推断]
- 快消型项目的 Spike 数量建议上限 3 个（防过度工程）；超出说明需求超出现有品类能力，应升级为长期迭代型或人工介入 [推断]

## 6. 效果度量建议（对齐 PRD §12 埋点体系）

- 新增埋点：`spike_created`（品类/触发判据）、`spike_verdict`（confirmed/refuted/partial）、`spike_timebox_hit`
- 目标指标：架构阶段后验收收敛轮次分布（对比历史 8 轮案例）；`PENDING` 决策点在架构文档中的存留数
- 归档对照：同一品类改造前/后各取 N 个项目做收敛轮次对照（对应 PRD §12.7 实验设计）
