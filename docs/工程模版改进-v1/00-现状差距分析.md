## 4. 差距的根因归纳

1. **G1 环境维度缺失 [文证]**：方法论 24 维 + 六模版章节结构（methodology §5.1）中没有任何"组件环境/系统依赖/外部服务"章节。模版只回答"代码长什么样"，不回答"机器上要装什么、怎么验证装对了"。
2. **G2 闭环样例缺失 [文证]**：模版有"测试策略"（分层比例、框架名），但没有一个"从架构到驱动到证据"的可照抄的本机闭环样例。昨晚 8 轮验收的每一轮本质都在补这个闭环。
3. **G3 坑库缺失 [实证]**：坑只在项目里被踩，踩完不沉淀，下一个项目（甚至同一项目的下一轮验收）再踩。desktop-app.md 0 条坑记录。
4. **G4 Spike 机制缺失 [文证]**：方法论没有任何"模版知识不足时怎么办"的条款。架构师只能现场踩坑，且实验产物（脚本/环境）没有规范位置，无法交给开发和测试复用。
5. **G5 标杆项目空转 [文证]**：21 个项目全部"待下载从未解析"，"参考项目"章节是未经证实的清单。模版的实证密度被高估。
6. **G6 技术栈单路径化 [实证+推断]**：desktop-app 只推荐 Tauri，实测走了 Python。缺少"快速验证路径（本机可验证优先）vs 正式交付路径"的双路径设计。
7. **G7 PRD 视角与工程视角断层 [文证]**：PRD §11 的"模板"是配置层（团队配置/流程/Sprint 节奏），S8 交付的"6 模板"是工程参考层。两层都存在，但 S8 验收标准没有"模版能否支撑一个真实品类项目一次跑通"的质量条款（sprint-plan L56 仅"6模板+自动推断"）。

## 8. 结论与改进方向

1. 现行模版是合格的"代码骨架参考"（v1 定位），但**完全不是"可运行性知识库"**——昨晚实测的全部踩坑都落在模版盲区。
2. 改进方向 = v2 结构规范七要素：①品类判定特征与反例 ②双路径技术栈矩阵 ③组件环境清单 ④测试闭环样例 ⑤Spike 实验协议 ⑥坑库 ⑦标杆项目映射（可解析的才保留）。详见 `01-模版结构规范-v2.md`。
3. 架构阶段需要配套流程增强（Spike 派发、产物落盘 00_SPIKES/、证据进 engineering.json 与 06_TESTS），详见 `03-架构阶段流程增强建议.md`。
4. 知识的可信度必须显式分级（已实证 / 文证 / 推断待验证），并在模版内用 Spike 编号挂接"待验证→已实证"的升级路径，使模版成为随项目演进的活文档。
