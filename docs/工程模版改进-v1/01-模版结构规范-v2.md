## 1. v1 → v2 的变化总览

| 维度 | v1（2026-07-17） | v2（本规范） |
|------|-----------------|-------------|
| 定位 | 代码骨架参考（"代码长什么样"） | 代码骨架 + 可运行性知识库（"机器上要装什么、怎么验证、哪里有坑、缺知识怎么办"） |
| 章节数 | 10 章 | 10 章（§0-§9，其中 4 章新增、2 章升级、4 章保留） |
| 技术栈 | 单路径推荐 | 双路径：快速验证路径（本机可验证优先）+ 正式交付路径 |
| 测试 | 分层比例 + 框架名 | 标准"架构→驱动→证据"闭环样例（可照抄） |
| 环境 | 无 | 组件环境清单（探测/安装/坑/降级 四元组） |
| 坑 | 散落在项目里（不沉淀） | 品类级坑库，条目带证据等级与状态 |
| 知识缺口 | 无处理机制 | Spike 实验协议（派子会话实验，产物回填模版） |
| 参考项目 | 清单式（可未验证） | 映射式：必须指明"看什么文件、验证什么"，未解析项目标注状态 |
| 可信度 | 无标注 | 每条关键知识标注 [实证]/[文证]/[推断] 三级 |

## 2. v2 标准章节结构（模板全文骨架）

每个品类模版必须按以下骨架撰写。`★` = 必填，`☆` = 按品类适配矩阵裁剪（见 §4），裁剪需在模版头部声明。

```markdown
# {品类名称} · 工程模板 v2
> 版本 / 代号 / 适用模式 / 证据等级图例 / 与 v1 的差异摘要

## 0. 品类判定 ★
  0.1 判定特征（≥3 条命中即归入本品类）
  0.2 反例与边界（易混淆品类 + 分流规则表）
  0.3 子形态（如双路径：快速验证路径 vs 正式交付路径）☆

## 1. 技术栈矩阵 ★
  1.1 快速验证路径（本机可验证优先：标准库/成熟库/最少系统依赖）
  1.2 正式交付路径（分发体积/性能/安全最优）
  1.3 选型决策表（什么条件走哪条路径）
  1.4 不建议方案（附理由）

## 2. 组件环境清单 ★  ← v2 新增，G1 对应
  2.1 组件总览表（组件/用途/必装性[必须|按需]/覆盖的功能域）
  2.2 组件卡片（每组件一张）：
      - 探测命令（一条命令判断已装/版本）
      - 安装方式（含系统包管理器与项目级两种）
      - 已知坑（版本/平台/环境变量）
      - 降级替代（装不上或不可用时的替代品）
  2.3 环境一键探测脚本（scripts/check_env.*，输出 JSON 证据）
  2.4 外部服务环境（云端 API：端点/鉴权/请求样例/常见错误）☆

## 3. 目录结构 ★（保留 v1）
  tree 视图 + 每目录职责；双路径项目给出两条目录树或差异标注

## 4. 核心配置 ☆（保留 v1）
  关键配置文件推荐内容（仅保留"照抄即用"级别的样例）

## 5. 测试闭环样例 ★  ← v2 由"测试策略"升级，G2 对应
  5.1 闭环定义：架构决定 → 驱动脚本 → 证据文件（三者缺一不闭环）
  5.2 本品类标准闭环：工具链 + 分步命令 + 期望输出 + 证据格式
  5.3 驱动断言规范：
      - expected/actual 严格同串（不得意译/意会比对）
      - 结果可见性：证据必须落盘（JSON/日志文件），不得仅依赖 stdout 或进程存活
      - 被测进程崩溃隔离：驱动须捕获退出码/日志并照常产出证据文件
  5.4 无头/受限环境降级验证（headless、回环、mock、录制回放）☆

## 6. Spike 实验协议 ★  ← v2 新增，G4 对应
  6.1 触发判据（何时模版知识不足，必须派子会话实验）
  6.2 任务书模板（引用 02-Spike实验协议.md §3，不重复正文）
  6.3 产物规范：工程目录 00_SPIKES/ 结构（实验报告 + 可运行环境脚本 + 证据）
  6.4 验收判据与时间盒
  6.5 知识回填：Spike 结论如何升级本模版的 §2/§5/§7 条目（[推断]→[实证]）

## 7. 坑库 ★  ← v2 新增，G3 对应
  条目格式（每条一张卡）：
      - ID：PIT-<品类缩写>-<序号>
      - 现象 / 根因 / 绕行方案 / 证据来源 / 状态[已实证|文证|推断待验证]
      - 若为推断待验证：挂接建议 Spike 编号 SPIKE-<NNN>
  7.1 平台级坑（OS / 窗口系统 / 音频系统 / 权限模型）
  7.2 栈级坑（框架/库版本、组合冲突）
  7.3 外部服务坑（云 API 端点/模型名/格式）

## 8. 标杆项目映射 ★  ← v2 由"参考项目"升级，G5 对应
  每品类 2-3 个：项目 / 本地或 GitHub 路径 / 看什么文件 / 验证什么结论 / 解析状态
  规则：未下载未解析的项目不得作为章节论据，只能列为"待解析"

## 9. 常见模式与反模式 ☆（保留 v1）
```

## 3. 关键设计决策与理由

### 3.1 品类判定放在 §0 并要求"反例"（对应 G6/G7）

v1 的"适用场景/不适用场景"是两行话。v2 要求给出**判定特征清单**（向导 Agent 可机械执行）和**反例表**（"用户说做桌面工具但其实是 Web 需求"的分流规则）。理由：昨晚实测暴露架构师在品类内还要做一次路径判定（Python 快速路径 vs Tauri 正式路径），这个判定应前移到品类判定阶段并有规则可依。

### 3.2 双路径技术栈矩阵，"本机可验证优先"（对应 G6）

v2 要求每个品类显式给出两条路径：
- **快速验证路径**：用本机最容易装、最容易驱动的栈先跑通"架构→驱动→证据"闭环（如 desktop-app 的 Python + pynput/sounddevice）。
- **正式交付路径**：分发/性能/安全最优的栈（如 Tauri v2）。
理由 [实证]：昨晚实测实际执行栈（Python）与 v1 模版唯一推荐栈（Tauri）完全不同。快速验证路径的产物（驱动脚本、环境清单、证据）同时就是 Spike 产物，可直接喂给正式路径的架构决策。

### 3.3 组件环境清单是 v2 的核心新增（对应 G1）

四元组（探测/安装/坑/降级）直接对昨晚教训建模：pynput 装了但没有 X 环境等于没装、portaudio 缺系统库时 sounddevice import 即崩、xrdp 环境无真实麦克风需要 .monitor 回环。**没有组件环境清单，架构师任务书里写的技术栈就是纸上谈兵**。每品类至少覆盖：运行时、关键三方库、系统级依赖、外部服务四类。

### 3.4 测试闭环样例必须"可照抄"（对应 G2）

v1 的"测试策略"表格（60/30/10 分层）对 Agent 没有可操作性。v2 §5 要求给出**本品类标准闭环的分步命令和期望输出**，验收标准是：一个没见过该项目的子会话，照抄 §5 能在本机产出第一个证据文件。驱动断言三条硬规则（严格同串 / 证据落盘 / 崩溃隔离）直接来源于昨晚教训 [实证]：expected 与 actual 字符串不一致导致误判、engine 崩溃导致结果不可见。

### 3.5 Spike 协议内嵌进每个模版（对应 G4）

v2 不把 Spike 当流程附件，而是作为模版的一等章节（§6），并定义**知识回填闭环**：Spike 结论把 §7 坑库的 [推断待验证] 条目升级为 [实证]。这使模版成为随项目演进的活文档，而不是一次性文档。

### 3.6 证据等级三级标注贯穿全文

- **[实证]**：本机真实跑通并留下证据（注明项目/日期）
- **[文证]**：有明确外部来源（官方文档/源码/已解析的标杆项目，注明路径或 URL）
- **[推断]**：分析推断，未经运行验证；必须挂接建议 Spike 编号或标"待验证"
理由：v1 的"参考项目"全部未解析却以确定语气书写 [文证：REFERENCE_PROJECTS.md 全部"⬜ 待下载"]，导致模版可信度被系统性高估。

## 5. 模版质量验收标准（对 S8 类交付的建议判据）

新模版（或模版新版本）合入前应通过以下检查（可在 03 文档流程建议中引用）：

1. **结构完整**：章节齐全且按本规范编号；裁剪项有声明。
2. **可照抄性抽检**：随机抽 §2 一个组件卡片、§5 闭环样例，由一个未参与撰写的子会话照抄执行，能产出证据文件。
3. **证据等级合规**：所有 [实证] 有项目/日期；所有 [推断] 挂接 Spike 或"待验证"标记；不存在无标注的确定性论断。
4. **坑库非空**：每品类至少 1 条 [实证] 或 [文证] 坑；desktop-app 品类至少覆盖 音频/注入/热键/托盘/云端 ASR 五个功能域。
5. **标杆映射可核**：§8 每个项目标注解析状态；"已解析"的项目必须真实存在于本地或给出解析报告路径。
6. **回填路径存在**：§6.5 说明 Spike 结论如何升级模版条目（能指出具体章节号）。

## 6. 版本与维护规则（沿用并强化 v1 methodology §6）

- 语义化版本：Major=结构/栈根变，Minor=新增坑库条目或组件卡片，Patch=修正/澄清。
- **新增回填触发器**：项目验收收敛轮次 > 3 时，强制复盘：哪些坑当时不在模版里 → 回填坑库并 Bump Minor（本事件即触发例：2026-09-17 实测 8 轮收敛 → desktop-app v2）。
- 模版源头与分发快照的关系维持现状（nanju-guide 09_工程模板 为源头，nanju-engineering-templates 为运行时快照），但两侧必须同版本号。
